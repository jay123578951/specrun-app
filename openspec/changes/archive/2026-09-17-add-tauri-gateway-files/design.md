## Context

見 proposal.md 的 Why。這裡只記影響做法的現狀。

七條路現在的分工與 T2 那四條相同：route 負責「讀寫檔案、列目錄、把失敗轉成可辨識的形狀」，`src/api/normalize-parked.ts` 與 `src/api/normalize-archived.ts` 負責「看懂內容、算進度、抽摘錄、分類錯誤、組裝成畫面要的資料」。兩者之間是一個中介形狀（probe）。normalize 是純函式、與執行形態無關，所以搬移的工作量只有前半段。

T2 已把「解析目標專案路徑」收斂成 `src/api/desktop/projects.ts` 的一個函式（canonical 化 → 取得檔案存取授權 → 確認是既存資料夾），七條路直接沿用，不必各自重做。

桌面形態手上已有的檔案通道：讀檔、寫檔、建目錄、搬移、刪除、列目錄、查基本資訊，權限清單七項齊備；`.git` 的遞迴放行在 T1 就寫進授權指令裡了。缺的只有一個「這個路徑存在嗎」的包裝（權限已在清單內）。

兩件事在 webview 裡沒有對應物，是本張所有做法差異的源頭：

- **Node 的路徑計算**。`node:path` 的接路徑、取上一層、算相對路徑、路徑分隔符，webview 一個都沒有。
- **作業系統的錯誤代碼**。Node 讀檔失敗時拿得到 `ENOENT`，據以分辨「檔案不在」與「檔案在但讀不到」；外殼的檔案通道只回一句人看的錯誤字串。

## Goals / Non-Goals

**Goals:**

- 桌面形態自行造出與 web 形態同形狀的 probe，餵給同一份 normalize，不重複任何解析或分類邏輯。
- 七條路的行為與 web 形態逐項對齊，包含各處的降級選擇——同一個專案在兩種形態下看到的東西要一樣。
- 路徑計算收斂成一份可單元測試的純函式，兩形態共用。

**Non-Goals:**

- 不動 web 形態的七條 route 與 `server/utils/` 底下的三個模組。
- 不改 normalize、不改任何畫面元件、不改 `OpenSpecGateway` 介面。
- 不動外殼（Rust）與權限清單。
- 不處理「勾選之後卡片進度數字要即時更新」（見下方決策 5）。

## Decisions

### 1. 路徑計算自己寫一份純字串模組，不用外殼的路徑 API

新增一個純函式模組：接路徑、取上一層、把絕對路徑換算成相對某個根目錄的路徑、判斷一個路徑是否落在某目錄底下。同步、不碰外殼、可直接單元測試。

**理由**：外殼的路徑 API **沒有「算相對路徑」這個能力**（有 join／resolve／dirname／basename／normalize，就是沒有 relative），而 park 的 artifact 快照非它不可——快照存的是 change 目錄內的相對路徑，存絕對路徑的話 repo 一搬家或改名，整份快照就失效，parked 詳情的 tabs 全開不出來。既然這一項一定要自己寫，其餘幾項一併用同一份，才不會在同一段程式裡混用同步與非同步兩套路徑工具（外殼的每一個路徑操作都是一趟跨行程呼叫）。

**曾考慮**：只補 relative 一個、其餘用外殼 API。同一個函式裡 `await join(...)` 和 `relative(...)` 交錯，讀起來像有兩套規則；而且 park 一次操作要算十幾條路徑，每條都是一趟往返。

**代價**：路徑語意變成自己維護的。以本張用到的範圍（絕對路徑之間的計算、`.`／`..` 一律在計算前就地收掉——這是逸出判定成立的前提）風險有限，以單元測試覆蓋兩種分隔符。

### 2. 「這個東西還在嗎」只問兩處：parked 詳情讀快照、archived 清單的 archive 根目錄

parked 詳情依 park 當下的快照逐一讀檔，讀之前先問一次該檔案是否存在：不存在就略過（缺件不是錯誤），存在卻讀不到才帶著錯誤往上報。archived 清單在列目錄之前先問一次 `openspec/changes/archive/` 在不在：不在就回空清單，在、卻列不出來才回報讀取失敗。這兩處以外不做這個詢問。

**理由**：只有 parked 詳情的讀檔清單來自**過去某一刻的快照**，清單與磁碟現況之間隔了一段時間，使用者可能在那段期間刪掉檔案。archived 詳情的 tabs 是現場列舉出來的，列得到卻讀不到本來就是真失敗（`src/api/normalize-archived.ts` 已寫明這個分工）；parked 與 archived 清單的讀檔失敗一律降級為「該卡片沒有進度／沒有摘錄」，本來就不區分原因。

**為什麼非分不可**：normalize 那一側對 parked 詳情的規則是「列進來卻沒有內容＝整個 change 讀不起來」。缺件若走到那一行，使用者只要手動刪過 parked change 裡任何一個 `.md`，那個 change 的詳情就再也打不開。

**archived 清單為什麼也要問**：`openspec/specs/archived-view/spec.md` 的「空與錯誤狀態」把「archive 目錄不存在或為空」與「清單讀取因檔案系統錯誤未完成」列成兩個 scenario——前者顯示空狀態文案、不顯示錯誤，後者顯示錯誤訊息並可手動重試。web 形態靠 `ENOENT` 分開這兩件事，桌面形態拿不到錯誤代碼，若把列目錄的失敗一律吞成空清單，「目錄在、讀不到」就會長得跟「還沒有 archived change」一樣，使用者連重試的按鈕都看不到。問一次根目錄在不在，不靠錯誤字串就分得開。archived **詳情**仍不問：它的 tab 清單是現場列舉的，列得到卻讀不到本來就是真失敗。

**曾考慮**：比對錯誤字串裡有沒有 "No such file"。認的是作業系統的文案，換版本或換語系就認錯。

### 3. park 可用性改用列目錄判定，不去查 `.git` 本身

判斷「這個專案能不能 park」時，列出專案資料夾、在結果裡找名為 `.git` 的那一項，看它是資料夾（一般 repo，可 park）還是檔案（worktree，禁用並提示不支援）；找不到就是非 git repo。

**理由**：桌面形態的檔案存取是白名單制，授權一個專案時連帶放行的是「`.git` 這個**資料夾**」——worktree 的 `.git` 是檔案，不在放行範圍內。沿用 web 形態「直接查 `.git` 是檔案還是目錄」的判法，在桌面形態會因為存取被拒而落進「查不到」的分支，把 worktree 誤報成「這不是 git repository」，提示說錯原因。專案資料夾本身一定在放行範圍內（每次讀取都在用），列它的內容會連隱藏項一起列出來。

**曾考慮**：在外殼的授權指令補一行，`.git` 是檔案時也放行它。要動 Rust，而且會把那個檔案的內容納入可讀範圍——只為了讀出「它是個檔案」這件事，不划算。

### 4. tasks 檔案位置的記錄，識別鍵加上專案

問過一次 CLI 之後把「這個 change 的 tasks 檔案在哪」記起來省下之後的呼叫（一趟約一秒，連按第二下會被吃掉）。記錄的識別鍵由「change 名」改為「專案路徑＋change 名」。

**理由**：本地 API server 是隨開發指令起落的短命行程，切專案的機會少；桌面 App 一開一整天，切專案是常態。兩個專案有同名 change（`add-settings-modal`、`add-live-refresh` 這類名字不同專案都會取）時，切過去之後那筆舊記錄還在、檔案也還在，勾選就會寫進另一個專案的檔案。寫入前的逐行比對多半擋得下來（跳衝突、勾不動），但兩邊那一行剛好一字不差時會安靜寫錯。勾選是全 App 唯一的寫入通道，代價是使用者真正的檔案。

**曾考慮**：切換專案時清空整份記錄。要在專案模組與勾選模組之間多一條通知線；識別鍵加一段字串沒有這個牽連。

### 5. 打包形態下勾選成功後，卡片上的進度數字不即時更新

勾選的成功路徑維持現狀：不做任何刷新。面板裡的 checkbox 是樂觀更新畫上去的，左側卡片的進度數字等檔案變動通知回來才重算——而通知還掛在本地 API server 上，T4 才搬。

**理由**：要讓它即時更新，得改 `src/stores/detail.ts` 的寫入流程，那是兩形態共用的一段，web 形態本來就靠通知更新，改了會讓它每次勾選多跑一趟 CLI。T4 一落地，兩種做法就沒有差別了。T1.6 與 T2 都立過同一個姿態——可觀察的中間態是預期結果，不是缺陷。

**代價**：本張做完到 T4 之間，用打包版勾任務時，面板裡打了勾、左邊卡片的數字不動，切頁回來才變。驗收要把這一項寫成預期行為，不要當成缺陷回報。

### 6. metadata 的整檔覆寫，暫存檔名用時間戳加亂數

park 的 metadata 沿用「先寫暫存檔、再改名蓋上去」的原子替換。暫存檔名現行是「檔名 + 行程編號 + .tmp」，桌面形態改為「檔名 + 時間戳 + 亂數 + .tmp」。

**理由**：webview 沒有行程編號可問。行程編號在原設計裡的作用是讓同時寫入的兩個行程不撞同一個暫存檔；時間戳加亂數達到同樣效果，而且桌面形態本來就只有一個寫入者。

### 7. 與 web 形態重複的那份實作不抽共用層

七條路搬過去之後，同一套規則會有兩份實作。沿用 T2 的裁決：不抽。

**理由**：web 那側 T4 整批刪除，屆時桌面那份自動成為唯一一份。為一個確定要消失的對象做抽象，抽出來的東西馬上就只剩一個使用者。兩份之間真正共用的部分（解析、分類、排序、摘錄）**本來就已經是共用的純函式**，重複的只是 IO 呼叫本身——而那正是兩形態唯一真正不同的地方。

**代價**：本張到 T4 之間，park 與 archived 的規則改動要改兩個地方。這段期間預期沒有規則改動（T4 是搬移不是改規則）。

### 8. park 與 unpark 動手前各自再取得一次授權

不吃「這個路徑授權過了就跳過」的記憶，park 與 unpark 一律先呼叫一次授權通道。

**理由**：授權通道是在「`.git` 是資料夾」時才連帶放行它的。使用者加入一個還沒 `git init` 的資料夾、之後才在裡面 `git init`，那個記憶會讓授權永遠不再重發，`.git` 因此一直不在放行範圍內——park 會失敗，而訊息會是存取被拒這種指向錯誤原因的話。重發一次授權的成本是一趟跨行程呼叫，只發生在使用者真的按下 park 的時候。

### 9. 勾選的排隊機制原樣搬

同一個 change 的「重讀 → 比對 → 寫回」不交錯，以 change 為單位排隊；不同 change 互不阻塞。

**理由**：桌面形態只有一個 webview，天然是單一寫入者，但同一個 change 連按兩下仍會讓兩次「重讀 → 寫回」交錯，後一次讀到的是前一次還沒寫回的內容。這與行程數無關，照搬。

## Risks / Trade-offs

- **改名搬移不是跨磁碟區的**：park 把 change 目錄從 `openspec/changes/` 搬進 `.git/specrun-app/parked/`，兩者同一個 repo 同一個磁碟區，整目錄改名是原子操作。→ 外殼的搬移通道語意與 Node 相同，此前提不變；跨磁碟區的情形不會發生，不另做複製後刪除的退路。
- **park 前要先問 CLI 拿快照，那一趟可能逾時**：快照必須在搬移前取得（搬走之後引擎就查不到這個 change）。→ 沿用現行規則：快照取不到就整個放棄、不搬移、不留半完成狀態，畫面上是一則失敗 toast、卡片回到原位。
- **路徑語意自己維護**：見決策 1 的代價。→ 單元測試覆蓋兩種分隔符與「落在某目錄底下」的逸出判定；這道判定是擋住 `..` 逃出 change 目錄的唯一防線，不能只靠字串開頭比對（`/a/bc` 不該算在 `/a/b` 底下）。
- **重複的實作在本張到 T4 之間並存**：見決策 7 的代價。
- **delta spec 裡有一個 scenario 的標題保留了舊用語**：`openspec-gateway` 的「路徑由伺服端解析」在桌面形態已無伺服端可言，但 delta 格式改 scenario 名等同刪掉它，驗證會擋。→ 標題原樣保留、內文改為形態中立的說法；要改名得等有 scenario 改名機制，或在某次 spec 整理時一併處理。

## Migration Plan

無資料遷移。`.git/specrun-app/` 底下的格式不變，兩形態讀寫的是同一份東西——同一個專案先用 web 形態 park、再用桌面形態 unpark，要能接得起來。

退路：桌面形態的七個方法各自獨立，出問題的那一條可以單獨改回委派給本地 API server（開發通路下仍併跑它），不必整張回退。
