## Context

摘錄的抽取端（`extractWhy()`）與呈現端（卡片 `line-clamp-2`）是兩套獨立訂定的規則：抽取端以「句」為單位、呈現端以「行」為單位，兩者從未協調過長度。動機見 proposal.md — Why。

既有規格中有一條理由需要一併處置：`docs/ui-structure-decisions.md` 記「品質天花板＝proposal 第一句寫作品質，接受之（反向形成寫作紀律）」。該理由預設 UI 的顯示結果會回饋到 proposal 的寫作行為，但 proposal 由 `opsx:propose` 產出，這條迴路不存在；真要約束寫作，槓桿在 `openspec/config.yaml` 的 `rules.proposal`，與 UI 無關。此理由 SHALL 於本 change 一併更換，否則下一次有人看到「兩行只用一行」時會依該理由判定為預期行為。

約束：`extractWhy()` 為 active（檔案直讀）與 parked（現場解析）兩條資料源共用的純函式，兩側摘錄必須逐字相同；純函式執行於伺服端，取不到卡片寬度、字級與實際斷行結果。

## Goals / Non-Goals

**Goals:**
- 抽取端與呈現端的職責切乾淨：抽取端決定「給多少內容」，呈現端決定「顯示多少」，兩邊互不預測對方。
- 移除句末判定後，連帶消除其已知缺陷，且不引入替代的啟發式規則。
- 舊決策的推翻理由落檔，避免日後被還原。

**Non-Goals:**
- 不調整卡片的兩行版位本身（行數、字級、卡片寬度皆不動）。
- 不改變摘錄的讀取範圍、來源路徑與降級行為。
- 不處理 proposal 的寫作品質——摘錄品質仍受首段寫作品質決定，本 change 只是不再額外損失內容。

## Decisions

### D1：抽取單位由「首句」改為「第一段全文」

段落有由空行界定的天然邊界，是這份資料裡唯一不需要啟發式判斷就能取得的單位。句子沒有這個性質——判定句末必須處理縮寫、版本號、檔名等歧義，而每一條規則都會有它自己的反例。

替代方案：
- **維持首句，改為填滿版位**：需要抽取端預測顯示行數，而行數取決於卡片寬度、字級與 CJK／拉丁字寬混排，純函式無從得知。以字元數近似的誤差在中英混排下可達兩倍。否決。
- **至多前 N 句／至多 N 字元且切在句界**：保留了句末判定的全部複雜度與缺陷，換得的只有「截斷不落在詞中」；而依實測，常用寬度下截斷率本就僅 16%。收益不足以支付其複雜度。否決。

### D2：截斷完全交給 CSS，不做任何伺服端長度處理

`line-clamp` 的截斷點落在實際可用寬度上，天然隨視窗縮放正確調整；伺服端的任何字數上限都會在某個寬度下截得太早或太晚。代價是截斷點不保證落在句界，摘錄可能結束於半個詞——已判定為可接受（卡片摘錄供快速掃視，需要完整內容時使用者本就會展開詳情）。

省略號一併交由瀏覽器產生，因為它是唯一「僅在確實溢出時才出現」且零成本的機制。

替代方案：
- **漸層淡出取代省略號**：可使截斷邊緣完全對齊，但純 CSS 無法做到「僅在溢出時套用遮罩」，需加入溢出偵測，否則未溢出的卡片結尾也會被淡化而傳達錯誤訊號。此外淡出的「還有更多」訊號較省略號弱。否決。
- **固定字數截斷後手動接省略號**：同 D1 的行數預測問題，且會在寬視窗下製造本可避免的截斷。否決。

### D3：段落不設字元上限

段落邊界即長度上限。實測 19 份既有 proposal 的第一段最長 251 字元，任何硬上限都落在無人會觸及的位置，只是憑空多一個需要日後解釋的魔術數字。若未來確實出現極長段落，其代價僅是清單回應多出數百位元組與 DOM 中一段看不見的文字，兩者皆無實質影響。

### D4：安全需求只改措辭，不改防線

`openspec-gateway` 的「讀檔範圍限定於引擎回傳路徑」中，摘錄例外的三項實質約束——只讀固定路徑 `proposal.md`、`<change-name>` 取自 CLI 輸出而非呼叫端輸入、路徑逸出視同讀取失敗——全數不變。變的只是外流單位由「單一句子」改為「`## Why` 第一段」，且明文維持「其餘段落與全文 MUST NOT 進入清單回應」。此為量的調整，非防線的鬆動。

## Risks / Trade-offs

- **截斷率隨視窗變窄而升高**（行寬 73 格時 16%、50 格時 68%、32 格時 95%）→ 已接受：省略號在窄視窗成為常態是「內容比版位多」的誠實呈現，且窄視窗下無論採何種規則都會截斷。
- **摘錄可能結束於半個詞**（尤其中文逐字斷行時）→ 已接受，並已於 `change-list` spec 明文立為可接受行為，避免日後被當成 bug 修回句界截斷。
- **螢幕閱讀器會讀出視覺上被截斷的內容**（`line-clamp` 僅視覺截斷，DOM 文字完整）→ 不予處理：輔助技術取得較完整的內容不構成傷害，且現行實作已是此行為，本 change 只是使其涵蓋的文字變長。
- **卡片高度的分佈改變**（僅佔一行的比例由約 50% 降至 5%）→ 為預期的正向效果：skeleton 依兩行高度製作，替換時的版面跳動隨之減少；`change-list` 既有的「摘錄不足兩行時的替換」scenario 仍需保留，該情形並未消失。
