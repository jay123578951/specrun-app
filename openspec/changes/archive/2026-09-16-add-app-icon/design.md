## Context

見 proposal.md「Why」。以下只記影響做法的現況與限制。

品牌記號在 App 裡是**算出來的**，不是圖檔：`src/components/BrandMark.vue` 每一幀呼叫 `src/utils/orb-engine.ts` 取得該幀的點清單，再用 `src/utils/orb-color.ts` 把每個點的明暗映射到 `--sr-surface` 與 `--sr-accent-bright` 之間，最後畫進 canvas。App 圖示需要的是一張定死的圖檔，所以中間必須有一個導出步驟。

三項實測結果框住了做法：

- **點全是半透明的**：定格幀 484 個點的透明度落在 0.594～0.806，沒有一個不透明。圖示沒有底就會透出桌布。
- **`tauri icon` 只吃一張來源圖**，沒有「不同尺寸餵不同圖」的選項（`--png` 只能改要產哪些尺寸，不能改來源）。
- **Node 24.13 可直接載入專案的 `.ts` 檔**：`import { MODE_FRAMES, resolvePreset } from '../src/utils/orb-engine.ts'` 在無建置、無額外套件的情況下執行成功，`orb-color.ts` 同樣可用。

`tauri dev` 產出的是 `src-tauri/target/debug/app` 這個裸執行檔，不是 `.app`，所以圖示換完不能靠 `pnpm dev:app` 驗收。

## Goals / Non-Goals

**Goals:**

- 圖示的幾何與上色與側欄記號同源——共用同一份程式，不另抄一份座標或色彩公式
- 產生器可重跑：記號設計日後變動，重跑一次指令就能更新圖示
- 零新增執行期依賴

**Non-Goals:**

- 不追求圖示與側欄記號逐像素相同（圖示另有底、另有亮度對應，本就不同）
- 不為小尺寸另做版本（規格已明訂，見 specs/brand-mark）
- 不檢視也不調校 Windows／Android 的圖示產出（ROADMAP 定案僅出 macOS）

## Decisions

### 幾何與上色共用既有模組，只新增三件事

產生器 `import` 專案既有的 `orb-engine.ts`（取得定格幀的點清單）與 `orb-color.ts`（把明暗映射到色票），新增的只有：亮度重對應、圓角底、縮放與輸出。

替代方案：把座標與色彩公式複製一份到產生器裡。否決理由——記號的幾何是逐字搬自上游套件、刻意保留原樣以便日後對檔比差異；再複製一份等於多一個會與上游脫鉤的副本。

### 在 Node 直接跑專案的 TS，不加建置步驟

已實測可行（見 Context）。替代方案是加 `tsx` 或先編譯，兩者都為了一支產生器引入建置通路，不划算。

### 自己畫像素、自己組 PNG，不加 canvas 套件

產生器以超取樣＋箱型縮小自行畫圓與線段，用 Node 內建的 `zlib` 組出 PNG。

替代方案：加 `@napi-rs/canvas` 之類的套件，直接沿用 `BrandMark.vue` 的 `ctx.arc` 畫法，忠實度最高。否決理由有二——一是為了一支產生器引入原生套件；二更關鍵：**使用者核可的圖就是這支自寫繪製程式畫出來的**，換套件會讓成品與已核可的樣子產生偏移。

代價記在 Risks。

### 單一來源圖交給 `tauri icon`，不走 `iconutil`

產生器只輸出一張 1024×1024 PNG，其餘全部尺寸由 `tauri icon` 產。

替代方案：自組 `.iconset` 目錄再用 `/usr/bin/iconutil` 打成 `.icns`，可讓 32px 與 16px 使用另外設計的簡化版。實測 32px 的簡化版明顯較清楚（環不會斷成不規則團塊），**但已由決策明確放棄**——換得單一來源、各尺寸同一個構圖。這不是遺漏。

### 定格取第 0 幀

`brand-mark` spec 既有「定格呈現的是起始那一幀」，圖示沿用同一條，不另立標準。

**這裡曾嘗試「挑一幀比較對稱的」，實測後確認不可行**：掃過一個週期的 48 個取樣時刻，每個點到圓心距離的起伏度全部是 0.0510，一個小數位都沒變。環的歪斜程度是固定的，動的只是歪向哪個方向。沒有更圓的一幀可挑。

### 亮度重對應：把當幀最暗與最亮兩端拉開成 0.55～0.95

產生器每跑一次都先掃過這一幀的每個點，找出最暗與最亮兩個端點，再把這兩端之間線性拉開成 0.55～0.95。**0.55 與 0.95 是寫死的，起點的兩個數字不是**——它們是當場量出來的，資料一換就跟著換。今天這一幀量到的是 0.44～0.70。另外把點的透明度整體乘 1.3（上限 1）。色票不新增，最亮端仍是 `--sr-accent-bright`。

這個做法有個副作用要記著：因為兩端取自當幀，輸出的亮度**永遠**是 0.55～0.95。日後 `orb-engine.ts` 隨上游更新、原始亮度區間漂移到別處（例如 0.30～0.80），重跑產生器出來的圖示在亮度上看起來會和現在一模一樣，漂移不會從亮度顯形；要察覺只能靠肉眼比對點與點的相對深淺，或看產生器印出的原始區間那行 log。這和下面 Risks 記的「`orb-engine.ts` 日後若隨上游更新，圖示會與記號不同步」方向相反：那則怕的是圖示跟著變、與已核可的樣子脫鉤，這裡怕的是圖示不變、讓人看不出上游已經變了。

**這裡曾嘗試「只拉透明度來提亮」，實測效果很小**：透明度本來就已有 0.59～0.81，拉滿也只差一點；真正壓住亮度的是顏色本身——原本最亮的點也只走到底色往 accent 高亮的 70% 處。槓桿在顏色對應範圍，不在透明度。這一條若沒記下來，下一個人會再走一次。

保留深淺差距是刻意的（spec 已規範）：對應到 0.85～1.00 那種更亮的設定會把整圈點壓成齊一亮度，環失去前後層次、看起來像平面圖形。

### 環上的刻度線畫成一筆，不是一串點

定格幀的 484 顆點不是隨機散佈：它是 **11 條同心環線 × 每條 44 個取樣位置**（484 恰好等於 11 × 44，沒有任何點被過濾掉）。畫面上看到的是**繞圈一周的 44 條放射狀短刻度線**，每條刻度線由 11 顆點疊成。點彼此是重疊的（最近鄰距離中位數 0.09，而兩顆點的半徑和約 1.0），所以看到的一顆顆不是縫隙，是半透明圓形交疊處的濃淡。

圖示把每條刻度線改畫成單一連續筆畫。做法：把點依繞圓心的角度分成 44 桶（實測每桶恰好 11 顆），對桶內的點擬合一條主軸，粗細與顏色沿主軸做線性擬合，再畫成一個膠囊形。

**這裡曾嘗試「把桶內的點依離圓心遠近排序、串成折線再描邊」，實測後確認不可行**：一條刻度線由內到外的明暗是 0.550 → 0.501 → 0.452 → 0.402 → 0.351 之後突然跳回 0.403，接著 0.300 → 0.381 → 0.320 → 0.361 來回震盪，相鄰間距也從 0.5 上下掉到 0.03。原因是外緣有兩條環線幾乎重疊，照遠近排序會把它們交錯排在一起。串成折線會把這個震盪忠實畫出來，每條刻度線上留一道明顯的接縫——比原本的點還難看。擬合才會把震盪抹平。這一條若沒記下來，下一個人會再走一次。

代價：擬合是把引擎算出的真實明暗拉成一條直線，所以圖示與側欄記號的明暗不再逐點對應。可以接受——圖示本來就另有底、另有亮度重對應，本就不是同一張圖。

「看不出是由圓點串成的」這句話在測試裡的量化判準是自己定的，spec 沒規定：沿刻度線的主軸量它的半寬變化，數這串數列有幾次由粗轉細（或反之）的轉折——連續的一筆至多 1 次，圓點串成的線每個接縫都會多一次。取 44 條的中位數而非逐條要求，是為了容忍個別刻度線主軸擬合的角度誤差；容忍度 0.75px 與門檻 1 是用新舊兩種畫法實際量測校準出來的。反向驗證過：把畫法改回逐點畫圓，這條測試量到 3 次轉折、正確轉紅。

**側欄記號不跟著改。** 實測把四種畫法都降到 64px 與 32px 比對，彼此已經分辨不出來，而側欄記號是 50px——改了看不出差別，卻要動 `BrandMark.vue`。所以側欄維持以點呈現，spec 明文記下這是圖示與側欄唯一的畫法差異。

### 版面數值

| 項目 | 值 | 理由 |
|---|---|---|
| 畫布 | 1024×1024 | `tauri icon` 建議的來源尺寸 |
| 超取樣倍率 | 4（先畫在 4096×4096 再平均縮成 1024） | 自寫的繪製沒有內建的邊緣平滑，圓與線段的平滑度全靠多取樣再平均；調高更平滑，但緩衝區與耗時都以平方成長 |
| 底的留白 | 四周各 9.77%（1024 內放 824 的方塊） | macOS 圖示網格慣例，滿版會比 Dock 裡相鄰 App 大一圈 |
| 底的圓角 | 超橢圓，指數 5 | 近似 macOS 的圓角曲線，比正圓角矩形接近 |
| 記號佔底 | 0.95 | 六個候選中使用者選定 |
| `>_` 佔記號 | 0.32 | 側欄是 50px 記號內放 16px 圖示，同一比例 |
| `>_` 筆畫 | 在 24 的繪圖框裡為 2.6 | **刻意不沿用側欄的 2.42**：那個數字是為了讓 16px 呈現時畫出 1.60px 筆畫而反推的，換到 1024 沒有意義 |
| 刻度線的粗細 | 沿線漸變，取該條線上 11 顆點的半徑對主軸做線性擬合 | 保留內細外粗的立體層次；等寬版本試畫過，環會變得平板 |
| 畫刻度線的順序 | 依每條線的平均深度，遠的先畫 | 與引擎對點的排序同一個道理；改順序會改變重疊處的疊色 |

### 產生器提交進 repo，不是一次性腳本

落在 `scripts/build-app-icon.ts`，由 `package.json` 的一個 script 呼叫。記號設計日後變動時重跑即可。替代方案是產生一次、只提交 PNG、腳本丟掉——否決理由：圖示會就此與記號脫鉤，下次改記號時沒人知道圖示是怎麼來的。

反過來，來源圖 `src-tauri/app-icon.png` 本身**不入庫**，已寫進 `.gitignore`：它由 `pnpm build:icon` 完整重生，入庫只會讓每次重生都多一份看不出差異的二進位 diff。「下次改記號時沒人知道圖示是怎麼來的」這個顧慮，由產生器在 repo 裡這件事解決，不需要再留一份可以推導出來的產物。各平台尺寸的成品（`src-tauri/icons/` 下 16 個檔案）則照常入庫，因為 App 打包直接讀它們。

## Risks / Trade-offs

- **自寫的抗鋸齒與瀏覽器 canvas 不同** → 圖示與側欄記號不會逐像素相同。緩解：圖示本來就有底與亮度重對應，本就不是同一張圖；驗收以肉眼對照為準，不做像素比對。
- **32px 與 16px 辨識度低**（環斷成不規則團塊、細節糊在一起）→ 這是決策的已知代價，不是缺陷。spec 已明文寫入，避免日後被當 bug 修掉。
- **`tauri icon` 會一併覆寫 Windows／Android 的圖示檔，未經檢視** → 緩解：ROADMAP 定案僅出 macOS，Windows 列為觀察項；那些檔案目前無人使用。
- **`pnpm dev:app` 看不到新圖示**（跑的是裸執行檔，不是 `.app`）→ 緩解：驗收改用 `tauri build --debug` 產出 `.app` 後在 Finder 與 Dock 檢視。
- **`tauri icon` 產出的檔案比要用的多**：`@tauri-apps/cli` 2.11.4 除了本次要的 16 個檔案，還會多產一個 `64x64.png` 以及 `android/`、`ios/` 兩個整個目錄。本次選擇全部刪掉、`src-tauri/icons/` 維持 16 個檔案。代價是日後每重跑一次 `tauri icon` 它們都會再冒出來一次，要再刪一次。另外實測：同一張來源圖連跑兩次，`icon.icns` 的位元組每次都不一樣（解出來的每張圖完全相同，差的只是 icns 容器本身的排法），所以重跑之後 `git status` 一定會看到 `icon.icns` 被改動，那不代表圖變了。
- **產生器取色值是抓 `tokens.css` 裡的第一個匹配**：Node 端讀不到 CSS 變數，產生器改用正則從 `src/styles/tokens.css` 抓 `--sr-surface` 與 `--sr-accent-bright` 的十六進位值，各取**第一個**匹配。目前這兩個變數各只定義一次，所以正確；日後若加上淺色主題那類覆寫區塊，它會靜默抓到第一個定義、不會報錯，圖示的顏色就與實際生效的色票對不上。
- **`orb-engine.ts` 日後若隨上游更新，圖示會與記號不同步** → 緩解：產生器提交在 repo，一行指令重生；此風險記入 tasks 的收尾檢查。

## Migration Plan

無資料遷移。圖示檔直接覆蓋，回退方式為 `git checkout` 還原 `src-tauri/icons/`。
