## Context

見 proposal.md 的 Why。這裡只記影響做法的現狀。

四條讀取路現在的分工，前三張 change 沒有動過：route 負責「跑指令、讀檔、把失敗轉成可辨識的形狀」，`src/api/normalize.ts` 負責「看懂輸出、分類錯誤、組裝成畫面要的資料」。兩者之間是一個中介形狀（probe）——原始 stdout、結束代碼、加上一批已讀好的檔案內容。normalize 是純函式、與執行形態無關，所以搬移的工作量只有前半段。

桌面形態手上已有的通道：外部指令執行（`spawn_bin`，帶逾時與輸出上限）、檔案讀寫與目錄列舉（fs plugin）、目錄授權（`allow_path`）、路徑組裝（Tauri path API）。缺兩樣——解開 symlink 取得實際位置，以及查詢檔案基本資訊的權限。

`src/api/desktop/cli.ts` 已有一個 `runCli`，但它把所有失敗壓成一個布林值，丟掉結束代碼與錯誤輸出。那是為側欄徽章寫的——徽章只要「數得出來或數不出來」。四條讀取路要靠這兩樣分類錯誤，得先把它換掉。

## Goals / Non-Goals

**Goals:**

- 桌面形態自行造出與 web 形態同形狀的 probe，餵給同一份 normalize，不重複任何解析或分類邏輯。
- 「解析目標專案路徑」在桌面形態收斂成一個地方，涵蓋 canonical 化、授權、存在性驗證三件事——T3 的檔案操作面直接沿用，不必各自重做。
- 兩形態對同一個專案得出同一個目標路徑。

**Non-Goals:**

- 不動 web 形態的四條 route 與 `server/utils/openspec-cli.ts`。
- 不改 normalize、不改任何畫面元件、不改 `OpenSpecGateway` 介面。
- 不做批次讀檔的外殼指令（見下方決策 5）。

## Decisions

### 1. 打包形態下還沒搬過去的四項功能，維持現行的錯誤訊息

Archived 整頁、任務勾選、加入專案、開啟所在位置在打包形態仍會失敗，訊息是傳輸層的原話（如「Could not read the archived list. Load failed」）。不另做「尚未支援」的標示。

**理由**：這四項在後兩張 change 搬完後自然可用，先做標示等於做完再拆。T1.6 已立過同一個姿態——可觀察的中間態是預期結果，不是缺陷。

**代價**：這兩張 change 的期間內，打包的 App 還不是日常可用的工具，勾任務仍得開瀏覽器。

**曾考慮**：在桌面形態把三個按鈕變灰、Archived 頁換成說明文字。要動四處畫面，且都要在 T3／T4 拆掉。

### 2. 目標專案路徑由外殼解開 symlink

外殼新增一個路徑正規化指令（Rust 的 `std::fs::canonicalize`），桌面端解析目標路徑時呼叫它。

**理由**：現行 spec 要求以 canonical 化後的路徑與引擎回報的 root 比對（`非 openspec 專案的判定以 root 路徑比對為準`）。openspec CLI 自己會解開 symlink 再回報 root，桌面端若只做字串層正規化，比對必然對不上——畫面上會把一個好好的專案說成「不是 OpenSpec 專案」。web 形態用的是 `realpath`，同一套語意。

**落點兩處**：解析目標專案時（處理設定裡既有的路徑），以及加入專案時（寫進設定的就是實際位置，兩形態的側欄才顯示同一個名字）。後者在本張沒有畫面入口可驗（選資料夾對話框要等最後一張），以單元測試覆蓋。

**曾考慮**：把判定放寬成不比路徑、只看引擎說它不是就地現造的。那會拆掉一道防線——加入一個本身沒有 `openspec/` 的子資料夾時，主區會默默列出上層專案的 changes。

### 3. 授權跟著使用走，不綁在某個動作上

解析目標專案時檢查該路徑是否授權過，沒有就授權，已授權的記在一個集合裡不重複呼叫。

**理由**：授權的入口不只一個——啟動時從設定載入、執行期切換、加入專案，三處都要。綁在動作上就是三處各寫一次，漏一處的後果是讀檔被拒、而畫面上看起來像是檔案不存在。綁在「使用前」只有一個地方。

**授權失敗**歸「目標路徑不是 OpenSpec 專案」類，細節帶外殼回的原話。與「資料夾不存在」同一類是因為使用者的處置一樣：換一個專案，或重新加入。

### 4. 指令執行結果換成完整形狀

`src/api/desktop/cli.ts` 的 `runCli` 改為回傳兩種結果之一：指令跑完了（帶結束代碼、stdout、stderr），或是沒跑成（帶已分類好的失敗）。四種沒跑成的情形——外殼拒絕（執行檔不存在或不可執行）、解析不出執行檔、逾時、輸出被截斷——在這一層就分類完，呼叫端不再看見外殼通道的原始形狀。

**理由**：兩形態的失敗形狀差很多。Node 那側是一個例外物件，用錯誤碼、`killed` 旗標分辨；外殼這側逾時與截斷是**帶旗標的成功回傳**，形式上是 `ok`。把分類收在這一層，四條讀取路各自只要組裝 probe，不必各自記得檢查那兩個旗標。

側欄徽章原本用的簡化判斷（「數得出來嗎」）在呼叫端自己收斂，行為不變。

### 5. 讀檔全部並行發出，不限流、不做批次指令

一份清單要讀 N 個 `proposal.md` 與 N 個目錄的建立時刻，一份詳情要讀該 change 的每一份 artifact。全部並行發出，與 web 形態同一個做法。

**理由**：側欄徽章之所以限流到 4，是因為每一項要跑一個 openspec 行程；讀檔不是同一個量級。進行中的 change 是個位數，總計數十趟通道呼叫，不值得為它補一個批次讀取的外殼指令——那會在外殼裡放一段「讀哪些檔案」的規則，而讀檔範圍限定於引擎回傳路徑這條要求，界線應該留在前端。

### 6. 模組切法

- `src/api/desktop/projects.ts` 補「解析目標專案」：canonical 化、授權、存在性驗證三件事收在一起，回傳可用的目標路徑或一個目標不可用的 probe 骨架。T3 的檔案操作面沿用同一個。
- 新增 `src/api/desktop/reads.ts`：四個 gateway 方法，以及它們共用的「跑指令 → 造 probe」與檔案讀取。
- `src/api/desktop-gateway.ts` 把四個方法接上去。

**理由**：沿用既有的按領域分檔（cli／config-store／projects／diagnostics）。目標專案的解析本來就住在 `projects.ts`，授權與 canonical 化是它的延伸而不是讀取面的私事。

## Risks / Trade-offs

- **引擎回報的 artifact 路徑落在授權範圍外** → 詳情讀檔會被拒。正常情況下那些路徑都在專案資料夾底下（已遞迴授權），但 custom schema 理論上指得出去。行為與 web 形態一致——該筆標為讀取失敗，其餘照常，不另做處理。
- **fs plugin 比對授權範圍時是否解 symlink 未經實測** → 授權的與讀取的都是 canonical 化後的路徑，兩邊一致時不受影響；實作時以一個 symlink 專案實測確認。
- **設定裡既有的路徑不是 canonical** → 目前不會發生（現存專案都是從瀏覽器那一側加的，已解過），但解析時一律再解一次，成本是每個專案一趟通道呼叫、且結果可快取。
- **過渡函式多活兩張 change** → `syncLocalServer` 留著，桌面端切換專案時仍補打本地 API server 一趟。刪掉的話，開發通路下切換專案後勾選任務會寫進另一個專案的同名 change，而畫面上看起來完全正常。本張只改寫它的解除條件：不是「下一張」，是「本地 API server 不再需要知道目前專案是哪個」。
- **查詢檔案基本資訊的權限一旦放行就撤不回** → Tauri 的檔案存取範圍只能加不能減。該權限的作用範圍仍受既有的路徑授權限制，不擴大可及的路徑。

## Migration Plan

無資料遷移。過渡策略沿用既有做法：桌面開發通路仍併跑本地 API server，四條讀取路換過去之後其餘領域照常經它。

驗收以打包形態為準——開發通路下本地 API server 還在，就算桌面端的實作有洞也可能被它掩蓋。
