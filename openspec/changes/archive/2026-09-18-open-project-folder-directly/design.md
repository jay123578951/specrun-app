## Context

動機見 `proposal.md` 的 Why。這裡只記動手時需要的現狀與約束。

兩個執行形態目前都把「開啟所在位置」做成同一件事——選取。桌面形態呼叫 opener 外掛的 `reveal_item_in_dir`（`src/api/desktop/opener.ts`），web 形態執行 `open -R`（`server/utils/reveal.ts`）。兩邊都只收一個路徑字串，不看它指向什麼。

`src-tauri/src/lib.rs` 已有一個既定模式：外掛的能力若經它自己的 JS 指令暴露給 webview 會帶來不想要的副作用時，改由自寫指令包該外掛的 **Rust API**。`pick_folder` 就是這樣寫的——對話框外掛的 JS 指令會在 `openspec/` 驗證之前把選定資料夾放進檔案可讀範圍，而那個範圍只能加不能減，所以改走 `FileDialogBuilder`。`spawn_bin`、`canonical_path`、`allow_path`、`allow_dir_listing` 同屬自寫指令這一層。

`src/api/desktop/shell.ts` 是外殼通道的薄層：只做型別與錯誤形狀的收束，不放商業規則。映射成商業結果（`RevealOutcome` 等）是上一層 `src/api/desktop/opener.ts` 的事。

`src/components/SettingsModal.vue` 的診斷區四行由一個 `rows` 陣列產生，其中 `revealable: true` 的兩行是設定檔與目前專案。這個陣列本來就分得出哪一行是什麼——`config` 那一行的值來自 `env.configPath`，`project` 那一行來自 `env.projectPath`。

`src/stores/settings.ts` 的 `reveal()` 只在失敗時做事：呼叫 `changesStore.notify()` 顯示一則全 App 共用的 toast。成功沒有任何畫面回饋（Finder 自己跳到前景就是回饋）。

## Goals / Non-Goals

**Goals:**

- 分岔的判定與開啟落在同一個地方，中間不經過前端。
- 桌面形態取得開啟資料夾的能力，而 `src-tauri/capabilities/default.json` 的權限清單一個字都不增加。
- 判定型別這件事不依賴任何檔案可讀範圍的授權——一個不需要讀取權的動作不該因為沒有讀取權而失敗。
- 兩個形態對同一個路徑走各自的通道，得到同一種結果。

**Non-Goals:**

- 不改 `RevealOutcome` 的三個狀態，不新增「那個位置已經不在了」這一態（見 D5 的取捨）。
- 不改能力旗標 `canReveal` 的語意與判定位置——它仍是一個旗標，不依型別分成兩個。
- 不改按鈕的位置、圖示、禁用三成因與其鍵盤行為。
- 不擴充 Windows／Linux 的支援範圍。Rust 端的實作天然跨平台，但 web 形態的 `canReveal()` 維持只認 macOS，本張不動它。

## Decisions

### D1. 型別判定與開啟合成外殼的同一趟，前端不先問型別

前端交出的是一個路徑字串，外殼收到後自己 `metadata()`、自己決定走哪一條，前端拿回的仍是「成功或失敗」。delta spec 的「呼叫端不需講明路徑的型別」由此成立。

**替代方案**：前端先呼叫一個「這是檔案還是資料夾」的通道，拿到答案再呼叫對應的開啟通道。

**不選的理由**：兩趟之間有一段空窗，而這個空窗的代價不對稱。`open_path` 對一個**檔案**路徑做的事就是交給預設程式開啟——

```rust
// tauri-plugin-opener 2.5.5，src/open.rs:54
pub fn open_path<P: AsRef<Path>, S: AsRef<str>>(path: P, with: Option<S>) -> crate::Result<()> {
    let path = path.as_ref();
    if with.is_none() {
        _ = path.metadata()?;   // 只確認存在，不分檔案或資料夾
    }
    open(path, with)
}
```

——那正是 `app-settings` 與 `openspec-gateway` 兩份 delta spec 都寫了 `MUST NOT` 的事，也是這顆按鈕當初存在的理由（`server/utils/reveal.ts` 檔頭：「設定檔按下去不該跳出編輯器」）。判定與開啟之間隔得愈久，兩者對不上的機會愈大。合成一趟不能消滅這個空窗（見 Risks），但把它壓到最小。

這個決定也讓兩個形態的分岔邏輯各寫一次而不是各寫兩次：桌面在 Rust 端、web 在 `revealPath()` 內，都是「摸一次、選一條」。

### D2. 桌面形態自寫指令包 opener 外掛的 Rust API，不開 `opener:allow-open-path`

`src-tauri/src/lib.rs` 新增：

```rust
#[tauri::command]
async fn open_in_file_manager(path: String) -> Result<(), String>
```

內部以 `std::fs::metadata` 判型別，**一般**資料夾呼叫 `tauri_plugin_opener::open_path(&path, None::<&str>)`，其餘呼叫 `tauri_plugin_opener::reveal_item_in_dir(&path)`。兩者都是 crate 的公開自由函式（`src/open.rs:54`、`src/reveal_item_in_dir.rs:12`），從 Rust 端呼叫不經過 IPC 的權限與 scope 檢查。`capabilities/default.json` 因此一個字都不動。

「一般」這兩個字是 D3 加進來的：macOS 的應用程式包（`.app`）在 `metadata()` 底下也是資料夾，而 `open_path` 對它做的事是啟動它。判定是不是應用程式包這一步因此不能省——它不是給開啟指令換個寫法就能繞過的事，見 D3。

宣告成 `async` 的理由同 `canonical_path`：tauri 只把 async command 丟到 async runtime，同步的會在主執行緒上跑完，而 `metadata()` 在網路磁碟區上的專案會卡住畫面。

**替代方案**：比照 `reveal_item_in_dir` 的現行做法，在 `shell.ts` 直接 `invoke('plugin:opener|open_path', …)`，並在 `capabilities/default.json` 加上 `opener:allow-open-path`。

**不選的理由**：那條路走不通，而且要走通的代價正是 proposal 擔心的那件事。查證如下（crate `tauri-plugin-opener` 2.5.5，即 `src-tauri/Cargo.lock` 實際解析到的版本）。

1. **這條權限只放行指令，不帶任何路徑範圍。** `permissions/autogenerated/commands/open_path.toml`：

   ```text
   [[permission]]
   identifier = "allow-open-path"
   description = "Enables the open_path command without any pre-configured scope."
   commands.allow = ["open_path"]
   ```

2. **但指令本體要求路徑範圍非空才放行。** `src/commands.rs:42-69` 的 `open_path` 吃 `CommandScope<Entry>` 與 `GlobalScope<Entry>` 兩個 extractor，把兩者的 allow／deny 併成一個 `Scope` 後呼叫 `is_path_allowed`，不通過就回 `Error::ForbiddenPath`。而 `src/scope.rs:139` 的判定末尾是：

   ```rust
   Ok(fs_scope.is_allowed(path) && self.allowed.iter().any(|e| e.matches_path_program(with)))
   ```

   `allowed` 為空時 `any` 恆為 `false`。也就是說，**只加 `opener:allow-open-path` 而不另外配置路徑範圍，`open_path` 會一律被拒**。

3. **要配置得能用，範圍必須涵蓋任意專案路徑。** 使用者的專案可以在任何地方，而 opener 的路徑範圍來自 capability 的靜態設定——它在 `is_path_allowed` 內即時由設定建出（`src/scope.rs:127-137`），沒有 `fs:scope` 那種 runtime 擴充的入口（對照 `lib.rs` 的 `allow_path` 走的是 `app.fs_scope().allow_directory()`，那是 fs 外掛的東西，管不到 opener）。所以能用的配置只有一個包山包海的 `**`，等於把「叫作業系統開啟任何路徑」整個開給 webview。

   這正是 `desktop-shell` 那條「開啟路徑不擴大檔案可讀範圍」要擋的方向。走 Rust API 則連這道 IPC 門都不開：webview 能請外殼開的路徑，只有自寫指令收下的那一個。

**與現行 `reveal_item_in_dir` 的差異要說清楚**，因為兩條權限的文字看起來一樣。`allow-reveal-item-in-dir` 的描述同樣是「without any pre-configured scope」，但那條指令的**本體**沒有 scope extractor（`src/commands.rs:72-76`，`add-tauri-gateway-opener` 的 design D5 已查證），所以它真的是無範圍放行。兩條指令是不同的東西，權限描述的雷同不能拿來推論。現行那條 `opener:allow-reveal-item-in-dir` 本張移除了：新指令取代 `shell.ts` 的 `revealItemInDir()` 之後它沒有呼叫者，開著沒人走的門不留——經過見 Risks 的「`shell.ts` 的 `revealItemInDir()` 可能變成沒有呼叫者」那一項。

### D3. 型別判定跟隨 symlink；應用程式包不算資料夾

`std::fs::metadata` 跟隨 symlink，取的是它實際指向的東西的型別（`symlink_metadata` 才是不跟隨的那個）。指向資料夾的 symlink 因此被當成資料夾，直接開起來。

理由：使用者按這顆按鈕要看的是那個東西本身，不是指過去的那張便條。專案路徑的 symlink 在加入專案時已由 `canonical_path` 解過一次，所以實務上這一條多半用不到；設定檔路徑則完全由 `configDir()` 產生，不會是 symlink。這條決定的作用是把「遇到了怎麼辦」講定，不是為了處理常見情形。

**開起來的那條交出的是解過之後的路徑**，不是前端交來的原字串——同一個立場貫徹到底：判定看解過的、開啟也看解過的。這同時把「判定完到開啟前被換成一個指向 `.app` 的 symlink」這條路收掉（見 Risks 的「型別判定與開啟之間不是原子的」那一項）。選取那條不必這樣做：`reveal_item_in_dir` 自己第一件事就是 `canonicalize`（`tauri-plugin-opener` 2.5.5，`src/reveal_item_in_dir.rs:13`），解不開就回 `Err`，不會反過來變成開啟。

**應用程式包（`.app`）在這裡不算資料夾**，走的是選取那一條，跟設定檔那一列同一個行為：Finder 跳到它的上一層並反白它，不執行任何東西。`metadata()` 說它是資料夾，但作業系統把它當可執行物件——這是第三種東西，不是「資料夾」與「檔案」二選一。

判定只看副檔名是不是 `.app`（忽略大小寫），取自解過 symlink 之後的路徑（Rust 的 `std::fs::canonicalize`、Node 的 `realpath`）。這不是權宜的猜測，是 macOS 認定應用程式包的實際依據，本機（Darwin 24.6.0）實測：

| 餵給 `/usr/bin/open` 的東西 | 結果 |
|---|---|
| `Foo.app`，包內結構完整 | 應用程式被啟動 |
| `Foo.app`，裡面只有一個純文字檔、連 `Contents/` 都沒有 | `open` 回「executable is missing」；`mdls` 仍報 `com.apple.application-bundle` |
| `Foo.APP`（大寫副檔名） | 應用程式被啟動 |
| 結構完整但目錄名不以 `.app` 結尾 | 當成一般資料夾瀏覽；`mdls` 報 `public.folder` |
| symlink 指向 `Foo.app`，symlink 自己不以 `.app` 結尾 | 應用程式被啟動 |
| `Foo.app/Contents`（包內的下一層） | 當成一般資料夾瀏覽；`mdls` 報 `public.folder` |

所以「包內有沒有 `Contents/Info.plist`」既非必要也非充分，不採用；副檔名清單只有 `.app` 一項，因為要擋的是「開啟資料夾這個動作啟動應用程式」，而 macOS 上只有 `.app` 代表應用程式。

**這條路只擋 `.app`，文件型的套件擋不住，而且我們接受這個結果。** `.rtfd`、`.xcodeproj`、`.workflow` 這些東西在檔案系統上也是資料夾（`isDirectory()` 為真），副檔名不是 `.app`，所以走的是不帶 `-R` 的那條，`open` 會把它交給對應的程式開啟——本機實測 `open -- Doc.rtfd` 會啟動 TextEdit 並開起那份文件，`mdls` 顯示這三種的 `kMDItemContentTypeTree` 都含 `com.apple.package`。

接受的理由是後果與成本不成比例：後果限於「一個已安裝的程式被叫起來開一份文件」，不是執行任意程式碼；而要正確分辨「這個套件會不會被交給某個程式開啟」必須去問 LaunchServices，純看檔案系統做不到，為此拉進一條系統查詢買不到相稱的保護。

**不可以拿「路徑只有兩個來源」當理由**——設定檔路徑由 `configDir()` 產生、專案路徑必須含 `openspec/` 才加得進來，這兩件事程式並沒有強制：`server/api/reveal.post.ts` 把 request body 的 `path` 原樣交給 `revealPath()`，不限來源；`src/api/desktop/opener.ts` 的檔頭自己也寫了「唯一的把關只有呼叫端」。所以這條路要當成「什麼路徑都可能進來」來想，接受的理由就只有上一段那一個。

一併記下好消息：「檔案」型的危險物（`.command`、`.terminal`、`.webloc`）不需要任何額外處理，它們 `isDirectory()` 為假，一律走 `-R` 選取，天然安全。

**不可行的替代方案**：把開啟指令馴服成「一律當資料夾瀏覽」。實測 `open -a Finder -- Foo.app` 與 `open -b com.apple.finder -- Foo.app` 都照樣啟動該應用程式——指名 Finder 只換了由誰來開，沒換「開」這個動作的語意。`open` 沒有任何旗標組合能達成這件事，唯一不啟動的形態是 `-R`，而那就是選取。

### D4. web 形態依型別在 `open` 與 `open -R` 之間選，不新增能力旗標

`server/utils/reveal.ts` 的 `revealPath()` 先 `stat`，是一般資料夾就 `execFile('/usr/bin/open', ['--', target])`，否則（含檔案與 D3 的應用程式包）維持 `execFile('/usr/bin/open', ['-R', '--', target])`。macOS 的 `open` 對一般資料夾的行為就是用 Finder 開起來。

兩條都帶 `--` 分隔旗標與路徑：以 `-` 開頭的路徑不加它會被 `open` 誤判成旗標（實測 `open -R -- -weird-file` 確實被當成路徑）。命令名寫成絕對路徑 `/usr/bin/open` 而非相對的 `open`：桌面形態那條經 opener 外掛的 `open` crate，在 macOS 上執行的就是 `/usr/bin/open`（crate `open` 5.4.4，`src/macos.rs`），兩個形態不因 PATH 解析結果不同而分家。

`canReveal()` 不動——它回答的是「這個平台辦不辦得到」，跟路徑指向什麼無關。`server/api/reveal.post.ts` 與 `src/api/web-gateway.ts` 都不動，它們只轉交路徑與狀態。

`stat` 失敗（路徑不存在、讀不到）時回 `{ status: 'failed' }`，與桌面形態 `metadata()` 失敗的結果一致。

### D5. 結果維持三態，失敗訊息收斂成單一句

`RevealOutcome` 的 `revealed | unsupported | failed` 不動。`revealed` 的讀法從「選取了」改成「開起來了」，涵蓋兩條分岔的成功。

`src/stores/settings.ts` 的失敗 toast 從 `Could not open the enclosing folder.` 改為 `Could not open that location.`——現行那句提到 the enclosing folder，對資料夾那一列已經不成立，無論如何要改。`unsupported` 那句（`Opening the enclosing folder is not available on this platform.`）同樣改成不提 enclosing folder 的寫法。

**替代方案**：多一個 `missing` 狀態，路徑已不存在時給一句「That folder is no longer there.」。

**不選的理由**：使用者拍板選單一句。**代價要記下來**：專案資料夾被搬走或刪掉之後再按那顆按鈕，畫面上只會說「開不起來」，分不出是「開啟失敗」還是「那個東西已經不在了」。實際用起來若嫌講不清楚，那是另開一張的事——它會動到 delta spec（多一條 scenario）與兩個形態的通道回傳值。

### D6. 按鈕文字由畫面自己分岔，不向通道查型別

`SettingsModal.vue` 的 `rows` 已經知道哪一行是檔案、哪一行是資料夾（`config` 來自 `env.configPath`、`project` 來自 `env.projectPath`），在該陣列上多帶一個欄位表達這件事即可，不另外向資料入口問一趟。

| | `title`（指標停留） | `aria-label`（輔助技術） |
|---|---|---|
| Config file | `Show in Finder`（維持現狀） | `Show config file in its folder`（維持現狀） |
| Current project | `Open in Finder` | `Open current project folder` |

`revealHint()` 目前在三個禁用成因之後 `return 'Show in Finder'`，改為依該行的種類回傳對應那一句。三個禁用成因的措辭一字不動——它們講的是「為什麼不能按」，與按下去會做什麼無關。`aria-label` 目前由 `Show ${row.label.toLowerCase()} in its folder` 樣板產生，改為各行自帶字串：兩行的句型已經不同，樣板拼不出來。

**這與 D1「前端不判型別」不衝突**，因為那是兩件事。按鈕文字是**按下之前的預告**，只要在正常情況下講得對；通道的判定是**按下當下的事實**，它錯了就會拿編輯器開檔案。專案路徑被換成一個檔案時，前端的靜態知識是錯的而外殼摸到的是真的——多的那一趟 `metadata()` 買的就是這個。

## Risks / Trade-offs

**型別判定與開啟之間不是原子的** → 無法消除，只能壓縮。判定（`metadata()` 加 `canonicalize()`）到 `open_path` 真的執行之間，同一台機器上的另一個程序若把那個位置換掉，開起來的就不是判定時看到的東西。**輸掉這場競賽的最壞後果是啟動一個應用程式**，不是跳出一個編輯器視窗——把該位置換成一個應用程式包即可。本輪為了認出應用程式包多摸了一次檔案系統（`canonicalize`），空窗因此比只摸一次時大一點。

已收掉的一半：開起來那條交出的是判定當下解過 symlink 的路徑（見 D3），所以「事後把路徑換成一個指向 `.app` 的 symlink」這條不再有效。剩下的一半消不掉——判定完之後把解出來的那個位置本身改名、或在原地換成一個 `.app`，開起來的就是換上去的東西。要真的關掉它必須一路持有檔案描述子開啟，而 `/usr/bin/open` 與 LaunchServices 只收路徑，收不了描述子。

這與 `lib.rs` 的 `allow_dir_listing` 檔頭記下的空隙同一性質（`is_dir()` 與 `allow_file()` 之間）：那裡的後果是一筆撤不回的檔案放行，這裡的後果是一個已安裝的程式被叫起來。把兩步放進同一個 Rust 指令是能做到的最小空窗。

**文件型的套件仍會被交給程式開啟** → 已知並接受，不緩解。這條路只擋 `.app`；`.rtfd`、`.xcodeproj`、`.workflow` 這類「在檔案系統上是資料夾、在 macOS 眼裡是一份文件」的東西走的是開起那一條，`open` 會把它交給對應的程式（實測 `open -- Doc.rtfd` 會啟動 TextEdit）。後果限於「一個已安裝的程式被叫起來開一份文件」，不是執行任意程式碼；要擋它必須去問 LaunchServices，純看檔案系統辦不到，成本與收穫不成比例。理由與實測出處見 D3。相對地，`.command`、`.terminal`、`.webloc` 這些「檔案」型的危險物 `isDirectory()` 為假，一律走選取，天然安全。

**判定多摸一次檔案系統** → 網路磁碟區上的專案會慢。兩個形態都以 async 處理（Rust 端 `async fn`、Node 端 `fs/promises` 的 `stat`），不卡住畫面。

**通用失敗訊息分不出「不見了」** → 見 D5，已知取捨，不緩解。

**`shell.ts` 的 `revealItemInDir()` 可能變成沒有呼叫者** → 新指令取代它之後，該函式與 `RevealItemInDirShellOutcome` 型別若無其他用途應一併移除，`capabilities/default.json` 的 `opener:allow-reveal-item-in-dir` 也跟著失去理由。動手時確認是否僅此一個呼叫點；是則移除，並在同一批改動裡拿掉那條權限，不留下開著卻沒人走的門。

**Rust 端的自動測試只蓋得到型別判定** → `open_path` 與 `reveal_item_in_dir` 真的會開起 Finder，測試裡不能呼叫。把型別判定抽成一個不碰外掛的小函式（收路徑、回「資料夾／不是資料夾／摸不到」），對它寫測試，比照 `allow_dir_listing` 既有的測試寫法；開啟那一步靠人工驗收。
