## Context

動機見 `proposal.md` 的 Why。這裡只寫實作要面對的現況。

全 repo 224 處規格文件引用的分佈與形態：

```
  形態                                        數量    拿掉之後
  ------------------------------------------ ------ ---------------------------
  （design D4）                               136    多數句子完整，刪括號即可
  （spec app-settings「驗證結果就地呈現」）      73    多數句子完整，刪括號即可
  見 openspec/changes/<name>/design.md D1        1    同上
  三段結構依 docs/ui-structure-decisions.md      1    同上
  M3／M4／C3／C4／C5 里程碑與批次代號           13    視句子而定
```

本次要動的是上表**之外**的判定結果——不看形態、看「刪掉之後還讀不讀得懂」：

```
  乙類  註解寫了禁令或規則，但「為什麼」整句不在註解裡
        BrandMark.vue:71
        /** 讀 visibilityState 與 reduced-motion，決定跑不跑——MUST NOT 用 hasFocus（design D4） */
                                                          +---- 有禁令 ----+  +- 無理由 -+

  丙類  編號是句子的文法成分，抽掉句子不成立
        settings.ts:34
        「套用失敗的訊息。與 `settings` 分開存是 design D6 的直接後果：…」
                                    +------ 抽掉 D6 這句話就斷了 ------+
```

兩個現況約束：

- 乙類的確切成員無法靠字串比對算出來。用禁令詞掃出 13 處候選，但其中部分的理由其實寫在上面幾行的區塊註解裡——那種是甲類，這次不動。必須逐條讀過原始碼才分得出來。
- 理由的原文散在 24 份已歸檔的 `design.md` 與 1 份進行中的。搬運時要回原文對照，不能憑印象重寫。

## Goals / Non-Goals

**Goals:**

- 乙丙兩類註解拿掉規格文件引用後，單獨讀就懂：規則、理由、以及「不這樣做該走哪條路」都在註解裡。
- 建立一份可以直接套用到第二批的改寫判準。

**Non-Goals:**

- 不動甲類的約 200 處（第二批）。
- 不動 `design.md`、`openspec/specs/`、`docs/` 等文件本身——理由留在那裡沒有問題，本次要切斷的是註解對它們的依賴。
- 不動任何 code 邏輯、變數名、格式。
- 不建立任何規範檔（見 D3）。

## Decisions

### D1 改寫的寬度：理由＋替代路

**選擇**：乙類每一處寫兩件事——「為什麼不能那樣做」，以及「真要達到那個目的該走哪條路」。約四行。

`BrandMark.vue:71` 的定案樣貌（已與使用者逐字確認，其餘乙類照此標準）：

```js
/**
 * 讀 visibilityState 與 reduced-motion，決定跑不跑。
 * 不看 hasFocus：視窗看得見但沒焦點，正是使用者最常瞥向記號的時候
 * （人在終端機跑指令、specrun 擺旁邊），拿焦點當開關會讓記號剛好在那時凍住。
 * 要再省電就降重畫頻率，不是改用焦點。
 */
```

**理由**：最後那句是收防的關鍵。只寫「為什麼不能用焦點」的話，日後真的要省電的人沒有別的路可走，還是會回頭改成 `hasFocus`；給了替代路，禁令才擋得住。

**考慮過的其他做法**：

- 只寫理由、不提替代路。註解最短，但擋不住為了省電而改回來的那次修改。
- 把 `design.md` 那段整段搬進來（連「可見度已涵蓋最小化、遮蔽、分頁切走」也寫）。這句讀 `document.visibilityState === 'visible'` 就看得到，屬於複述 code，`comment` skill 的判準本來就要求刪掉這種。

### D2 丙類重寫時，保留編號承載的事實、丟掉編號

丙類的編號有時夾帶了一個真實資訊。例如 `BrandMark.vue:14`「design D7 實測值：波紋繞一圈約 2.9 秒」——`D7` 要丟，但「這個數字是量出來的、不是推算的」要留，寫成「實測波紋繞一圈約 2.9 秒」。

**理由**：把編號當代名詞用的句子，拆開後常剩下一個有用的限定詞（實測／定案／推翻）。整句刪掉會連那個限定詞一起丟。

### D3 改寫後不得留下任何指向規格文件的字串，包括 change 名

**選擇**：改寫後的註解裡不能出現 `design D4`、`spec app-settings`、`.md` 路徑，也不能出現 `add-orb-logo design D4` 這種補上 change 名的版本。

**理由**：補 change 名只是讓引用變得找得到，人還是得離開程式碼去翻文件。使用者要的是「註解自己就能說明」，不是「引用寫得更完整」。

**考慮過的其他做法**：全 repo 統一改成帶 change 名的引用格式（`docs/ui-structure-decisions.md` 目前就是這樣寫）。這解決了「翻不到」，沒有解決「要翻」。

### D4 不在本 repo 立「註解須自足」的規範

**選擇**：不新建專案 `CLAUDE.md`，不動 `openspec/config.yaml`。規範層交給已記進跨專案回饋收件匣的條目，日後統一修 kit 層的產碼規範。

**理由**：規範只住一個地方，不會專案與 kit 兩邊各自演化。

**已知代價**：從本次改完到 kit 層修好之間有一段空窗期，期間新寫的 code 沒有任何規範可讀，可能再長出新的引用。使用者知情並接受。

**註記**：寫進 `openspec/config.yaml` 的 `context` 段沒有用——那段的作用範圍是「產 artifact 時給 AI 看」，而這些引用寫在 `.ts`／`.vue` 裡，寫 code 的人讀不到。

### D5 丙類靠機械特徵掃，乙類靠人逐條讀

**選擇**：兩類的找法不同。

丙類有機械特徵——引用後面接「的」「：」「實測」「定案」，代表它被當成句子成分在用。`grep -rnoE "(design D[0-9–、／/]+|spec [a-z-]{4,})( 的|：|\s+實測|\s+定案)" src/` 掃得出 17 處，再人工補同型變體（`（design D3 打樣結論）`、`（design D3 v3）`）。收尾時重跑同一條指令、結果為空，就是這類已經清乾淨。

乙類沒有機械特徵。「理由有沒有寫在註解裡」是語意判斷，掃不出來——用禁令詞掃出的 13 處只是近似解，其中部分的理由其實寫在上面幾行（那是甲類）。必須逐條讀完整段註解。

**理由**：一開始只靠肉眼挑丙類，挑出 8 處；改用機械特徵掃，發現 `changes.ts`、`PanelShell.vue`、`types.ts`、`orb-color.test.ts` 等檔還有同型的，實際是 17 處。有機械特徵的就別靠眼睛。

### D5b 乙類成員由實作時逐條判定，判準先寫死

**選擇**：不預先釘死名單。判準固定為「註解寫了禁令或規則，但『為什麼』整句不在這段註解裡」；13 處候選逐條讀過確認，命中就改，沒命中就留給第二批。

**理由**：候選是用禁令詞掃出來的近似解。實際讀過會發現兩種偏差——有些候選的理由寫在上面幾行（屬甲類），有些沒命中禁令詞的其實是乙類（例如 `detail.ts:20`「design D6 的資料路徑分流」）。名單先釘死反而會讓實作照著錯的名單做。

這是刻意留給實作的留白，不是遺漏。

### D6 分兩批，本次只做乙丙

**選擇**：本次只做乙丙類。甲類約 200 處由 `strip-spec-citations-from-comments` 承接——該 change 已同時建立，但**實作要排在本 change 之後**：它的範圍是用排除法定義的（「本 change 判定後沒動到的其餘所有引用」），順序顛倒的話，乙類那些只寫規則沒寫理由的註解會被當成一般出處直接刪掉，理由就跟著沒了。

**理由**：乙丙每一處都要人判斷理由寫得對不對，甲類只是刪括號、句子一字不動。混在同一份變更清單裡，要判斷的二三十條會被掃過即可的兩百條淹沒。也合本專案「寧可多個小 change 也不要一個大 change」的慣例。

## Risks / Trade-offs

- **理由從 `design.md` 搬過來時走樣或搬錯** → 每一處都要回原始 `design.md` 對照原文，不憑印象重寫；改寫後在報告裡並列「原文出處」與「改寫結果」供人工逐條核對。
- **乙類漏判**（該改的被當成甲類留下） → 13 處候選逐條讀完並在報告中逐條交代判定結果（改了／判為甲類留給第二批），讓漏判看得出來而不是消失。
- **`BrandMark.vue` 與進行中的 `add-orb-logo` 是同一個檔案**，兩邊都動註解區 → 本次要動的四處（`:12`、`:14`、`:71`、`:124`）都在註解，不碰邏輯；實作前先確認該檔沒有未提交的改動。
- **`comment` skill 的判準抓不到這種寫法**（它會把 `（design D4）` 判定成「在講 why，保留」）→ 本次靠人工判定，不依賴該 skill；規範層的修補見 D4。
- **空窗期會長出新的引用**（D4 的已知代價） → 接受。

## Migration Plan

純註解改動，無部署與回滾議題。

第二批（`strip-spec-citations-from-comments`）已同時建立規格，但要等本 change 人工驗收通過後才開始實作。第二批的內容是機械刪除——把句尾的 `（design Dn）`、`（spec <名>）`、`.md` 路徑與 `M`／`C` 代號拿掉，句子其餘部分一字不動；若刪完發現句子讀不通，代表當初分類分錯，該處退回本次的乙丙判準處理。
