## Context

動機見 proposal.md「Why」。這裡只記三件影響作法的現況。

**設定檔是整檔覆寫。** `app-config.ts` 的寫入是讀回整份、改一欄、整份寫回；`project-state` 與 `cli-resolver` 各自都這樣寫過。兩個行程同時持有就會互相蓋掉。

**「目前專案」是執行期狀態，不是每次重算。** `project-state` 在行程內快取一份，切換是一個明確動作。本地 API server 的切換掛載點除了更新狀態，還負責把檔案變動監看換掛到新專案。

**過渡期兩個行程並存。** 本 change 只搬設定與 CLI 解析，讀取面仍由本地 API server 服務，而它需要知道「現在是哪個專案」。

## Goals / Non-Goals

**Goals:**

- 桌面形態自行持有設定與 CLI 解析，不經本地 API server。
- 兩種執行形態共用同一份設定檔。
- 外殼的指令執行通道不會因為使用者的 shell 設定檔卡住而讓 App 失去反應。
- 過渡期間，切換專案在兩個行程之間保持一致。

**Non-Goals:**

- 不改變設定檔的格式與欄位，不做搬移轉換——同一個檔案，只是換人讀寫。
- 不改變 CLI 解析的優先序與三段降級語意，只換執行通道。
- 不改 `OpenSpecGateway` 介面，畫面端零改動。

## Decisions

### D1 依執行形態分流，介面不變

`src/api/gateway.ts` 依 `isTauri()` 分流。桌面實作承接七個方法：專案清單、加入、移除、切換、CLI 設定、套用路徑、重新偵測。

三個來源檔的純函式部分原樣沿用——設定內容解析、解析優先序、命令位置挑選、版本字串挑選都已是可注入設計，測試也已覆蓋。只有真正碰檔案與跑指令的部分換成外殼通道。

**替代方案：桌面端每次讀取前先跟本地 API server 要「專案路徑＋執行檔」。** 否決——四條讀取路每一條都要多繞一趟，而且這段程式在讀取面搬完後整批作廢，丟棄的量比本方案大。

**替代方案：只搬一半（例如專案清單搬、CLI 路徑不搬）。** 否決——兩個行程都會整檔寫回同一個設定檔，使用者剛加入的專案會在設定 CLI 路徑之後消失。

### D2 設定檔沿用現有位置，不用外殼預設的資料目錄

外殼預設的資料目錄以套件識別名命名（`dev.specrun.app`），與 web 形態實際使用的目錄（`specrun-app`）不是同一個。沿用後者，兩形態共用。

理由是使用者感受得到的：同一台機器上，用開發通路開跟點 App 開，看到的必須是同一份專案清單。若各用各的，切換形態就像換了一台電腦。

外殼的靜態放行範圍因此改指這個共用目錄。三個平台的位置由既有的設定目錄解析函式決定，該函式的平台分支已有測試；桌面端改由外殼的路徑通道提供家目錄與平台別，其餘不變。

**替代方案：改用外殼預設目錄，並在首次啟動時搬移舊設定。** 否決——搬移只解決一次，之後兩形態仍是兩份；而開發期同時用兩種形態是常態。

### D3 原子寫入沿用 temp + rename

外殼的檔案通道已具備建目錄、寫檔、改名三項能力，靜態放行範圍涵蓋設定目錄，因此現有的「同目錄暫存檔寫完再改名」可原樣沿用，不需要另設鎖。

### D4 指令執行通道加逾時，逾時即終止行程

外殼目前的執行通道會一直等到指令結束。借 login shell 偵測會執行使用者自己的 shell 設定檔，那裡面卡住就會讓整個 App 沒有反應。

通道改為接受逾時毫秒數，逾時則終止該行程並回傳可辨識的逾時結果。呼叫端沿用既有的三個上限：資料請求 15 秒、`--version` 驗證 5 秒、login shell 偵測 3 秒。

同一個通道也接受輸出位元組上限。理由與逾時同源：輸出全數收在記憶體裡，失控的指令（誤指到會一直印東西的程式）同樣能拖垮 App。超過上限即停止累積並標記為截斷，呼叫端一律視同該次呼叫失敗——被截斷的 JSON 解析出來是錯的答案，比沒有答案更糟。

作法上用非同步的行程通道搭配逾時等待（外殼的執行環境已具備），不用輪詢。若該途徑在此版本不可行，備案是另開執行緒等待、逾時由主執行緒終止行程——兩者對外行為相同，不影響規格與任務拆法。

### D5 命令位置還原改用非互動 shell

自動偵測第一階段命中後，畫面上要顯示的是絕對路徑而不是命令名，因此需要把命令名還原成路徑。現行作法是逐一走過行程自己的 PATH 找可執行檔——桌面端的前端沒有行程環境變數可讀。

改為透過執行通道跑一次非互動 shell 的 `command -v`。與第二階段的差別要講清楚：第二階段用的是**互動式登入** shell（會跑使用者的設定檔，所以才需要 3 秒上限），這裡用的是非互動 shell，不跑設定檔、只查當下環境。兩者用途不同，不是同一段的重複。

這不違反「不得維護一份寫死的常見安裝位置清單」——查的仍是當下真正的環境，只是換了一種問法。

### D6 診斷中尚未具備的項目回報為未知，不回 false

環境診斷有五項，其中「檔案變動通知是否運作」與「能否開啟檔案所在位置」兩項的通道還沒搬到桌面形態。

回 `false` 是錯的：過渡期間監看其實由本地 API server 在跑，桌面端只是問不到它，回 false 等於斷言「沒在跑」。型別因此放寬為可為未知，畫面上以「—」呈現，區別於明確的「是／否」。

### D7 過渡期的切換一致性：桌面端切換後通知本地 API server

桌面端切換專案會寫進共用設定檔，但本地 API server 在自己的記憶體裡另有一份狀態，而讀取面還靠它。不處理的話，側欄切了專案、主區清單還停在舊專案。

桌面端的切換、加入、移除三個動作成功後，額外呼叫一次本地 API server 既有的切換掛載點。那個掛載點順帶會把檔案變動監看換掛到新專案——一趟解決兩件事。

設定檔的寫入權整趟留在桌面端。那個掛載點手上的設定是它啟動時讀進去的，讓它整檔寫回會把桌面端剛寫的內容蓋成舊值，因此這一趟帶一個旗標讓它只更新自己的執行期狀態。同一個理由往下推一層：它的專案清單也是那份舊快照，用來判斷「這個專案在不在清單裡」會否決掉桌面端剛加入的專案，所以帶旗標的那一趟先重讀一次設定檔再判。不帶旗標的呼叫端行為完全不變。

這段程式的壽命明確：讀取面搬完（下一張 change）之後刪除。呼叫失敗不讓操作失敗，只是這一次的主區清單會落後；再切一次即可對齊。

**替代方案：讓本地 API server 每次請求重讀設定檔、不持有狀態。** 否決——那會退回到「目前專案」不是明確動作的舊模型，動到的是尚未搬移那一側的核心設計，過渡期結束後還要改回來。

## Risks / Trade-offs

**中間態的畫面看起來像做壞了** → 本 change 完成後，打包的 App 側欄有專案、Settings 有 CLI 狀態，但主區是錯誤訊息，「加入專案」也還按不動——它的唯一入口是原生選資料夾對話框，而那條通道要到最後一張才搬，打包形態沒有本地 API server 可問。因此打包形態驗收時側欄的專案得先由開發通路加好。在 tasks 的驗收條目寫明這些都是預期結果，並說明主區與加入專案各自恢復是哪一張的事。

**D7 的同步呼叫是丟棄式程式** → 承認它存在，範圍限制在三個動作各一次呼叫，並在下一張 change 的任務清單裡列為必刪項，避免它留下來變成永久的雙寫。

**login shell 偵測第一次真的被執行** → 這正是本 change 提前的目的。若在此發現該途徑在打包形態下不可行（例如外殼環境取不到使用者的 shell），還有三張 change 的餘裕改走「引導使用者手動指定路徑」的既有出口，而不是發佈前才發現。

**共用設定目錄不在外殼預設範圍內** → 靜態放行範圍改動後，要確認未經授權的其他路徑仍被拒絕，既有的邊界需求不因這次放寬而失守。

**設定檔寫入失敗的降級** → 現行兩處寫入都是靜默降級（寫不進去不影響本次操作）。桌面端沿用同一姿態，不因換了通道就改成拋錯。

## Migration Plan

1. 外殼先加逾時與放行範圍調整——這兩項不改變 web 形態行為，可獨立驗證。
2. 設定與 CLI 解析的桌面實作接上，`gateway.ts` 分流。
3. 以開發通路驗證兩形態共用同一份設定：一邊加入專案，另一邊重開後看得到。
4. 打包後驗證 login shell 偵測——這是本 change 的關鍵驗收點，必須以點開 `.app` 的方式進行，開發通路驗不到。

回退方式：`gateway.ts` 的分流改回恆用 web 實作即可，桌面實作留著不生效。設定檔格式未變，回退後 web 形態讀得到桌面形態寫過的內容。

## Open Questions

- 外殼指令通道的逾時要不要對「終止後仍未結束的行程」再補一層強制終止。現行的 15／5／3 秒場景下，被終止的都是短命指令，補這層的價值待實際使用觀察，且不影響規格與任務拆法。
