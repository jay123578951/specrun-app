## Context

動畫來自 thinking-orbs（MIT，Copyright (c) 2026 Jakub Antalik，github.com/Jakubantalik/thinking-orbs）。動機見 proposal.md - Why；行為契約見 `specs/brand-mark/spec.md`。

三個限制決定了整個做法：

1. 套件的 `peerDependencies` 要求 React ≥18，本專案是 Vue 3——不能安裝。
2. 套件只畫灰階（`rgba(v,v,v,a)`），而本專案的規矩是 accent 為唯一顏色、元件不得寫死色值。
3. App 目前只有深色主題（`tokens.css` 的 `:root` 單一色板、`color-scheme: dark`），套件那套三層深淺色偵測用不上。

拆開套件看，React 綁得很淺：

```
engine.es.js  557 行  全域搜尋 "react" = 0 次
   ├── 幾何：吃 (size, t, opts)，吐出「這一幀有哪些點、各在哪、多亮」
   │        純 Math、不碰 DOM、不知道 canvas 存在
   └── 上色：把那串點畫到 canvas 2D 上，十幾行

index.es.js   130 行  React 專屬：canvas ref、每幀重畫迴圈、
                      深淺色偵測、減少動態的定格、
                      分頁切走與捲出畫面時暫停
```

作者自己在 `engine/types.d.ts` 寫明這是刻意的：幾何那半是為了能被搬到 React Native 與 SwiftUI 而設計成無閉包、只用 `Math`。

## Goals / Non-Goals

**Goals:**

- 搬進來的第三方程式碼維持可比對——日後上游更新時能直接對檔看差異
- 動態的份量落在「看得到它活著」與「不會一直想去瞄它」之間，且有實測依據而非憑感覺
- 重畫迴圈在該省的時候省，在該動的時候不被誤停

**Non-Goals:**

- 不做通用的點球元件。只有 breathing 一種形態、一種尺寸；其餘八種狀態不引入
- 不支援淺色主題。等 App 真的長出第二套主題再回來處理
- 不接 watcher。記號恆定，理由見 spec 的「動態與 App 狀態無關」

## Decisions

### D1 搬入幾何運算，自寫 Vue 包裝

**選擇**：把 `engine.es.js` 整份搬進專案（幾何部分一字不改），另寫一個 Vue 元件取代 `index.es.js` 那 130 行。

**理由**：幾何那半只需要一個 canvas 2D 繪圖脈絡，與框架無關；要重寫的只是 canvas ref、每幀迴圈與幾個瀏覽器事件，在 Vue 裡是同樣份量的程式碼。

**考慮過的其他做法**：

- 安裝套件並引入 React——為了一個 50px 的記號背一整套框架，不成比例
- 只看視覺、用 CSS／SVG 自己重做——那 557 行是球面投影加各模式的數學，CSS 重刻不出來
- fork 整個套件再改——會連 React 那層一起維護，比重寫貴

### D2 用 size 64 的設計，讓 CSS 縮到 50px

**選擇**：向 `resolvePreset('breathing', 64)` 取參數，畫布給 `64 × dpr`（一般螢幕為 128 device px），CSS 寬高設 50px。

**理由**：套件的 20 與 64 是兩份各自調過的設計，不是同一份縮放。實測差距：

```
              20 的設計    64 的設計
一圈取樣點數      15          44
疊幾圈             8          11
總點數           120         484
波動幅度       0.565       0.368
```

一圈只有 15 個取樣點時，8 圈點在同一角度上徑向黏成短橫槓，波紋繞圈也看得出一格一格跳。用 64 的設計畫進 128 device px 再由 CSS 呈現成 50px，等於 2.56 倍的資訊量換邊緣細緻度。

**考慮過的其他做法**：

- 直接用 20 的設計——就是上面那個粗且跳的結果
- 用 64 的原尺寸顯示——品牌列會從 68.6px 漲到 99px，清單下移 30px，代價翻倍

### D3 只換上色那一層，幾何原封不動

**選擇**：呼叫幾何函式取得該幀的點清單，自己寫 painter；不改幾何的任何一行。

**理由**：套件本來就把幾何與上色分開，幾何產出的每顆點帶一個明暗值。只換 painter 的話，搬進來的幾何與上游完全相同，日後比對成本最低。

染色把明暗值 `v = 1 - white` 直接拿去在 `--sr-surface` 與 `--sr-accent-bright` 之間取值，**不墊下限**。墊了下限（例如把最暗的點限制在 25%）會壓縮深淺差距，點就失去前後層次、糊成一根根短橫槓——這是打樣時實際踩到的。

### D4 迴圈只看「看不看得見」，不看焦點

**選擇**：以 `document.visibilityState` 決定跑不跑，不使用 `document.hasFocus()`。

**理由**：視窗看得見但沒有焦點，正是使用者最常瞥向記號的情境——人在終端機裡跑指令，specrun 擺在旁邊。用焦點當開關會讓記號剛好在那時候凍住。可見度仍然涵蓋最小化、被完全遮蔽、分頁切走這些真正該省的情況。

**考慮過的其他做法**：失焦即停。省得更多，但省在錯的地方。若日後真的需要進一步省電，該走的是降低重畫頻率（speed 0.6 下一圈 2.9 秒，30fps 肉眼分不出來），不是拿焦點當開關。

### D5 定格先畫，再決定要不要跑迴圈

**選擇**：元件掛上後無條件先畫一幀，之後才判斷要不要進入迴圈。

**理由**：打樣時把「不可見就不啟動迴圈」寫成唯一入口，結果第一幀還沒畫就被判定不用跑，畫布從頭空到尾。停止不等於空白——這條寫進 spec 是因為它不是效能問題，是使用者會看到一個洞。

### D6 中央符號取既有的 lucide terminal

**選擇**：用專案已安裝的 `@iconify-json/lucide` 裡的 `terminal`，筆畫調細後置中疊在環上方。

**理由**：它講的話永遠成立——這個 App 的引擎確實整包外包給 openspec CLI（見 config.yaml 的專案脈絡），而不是某個會變成假的狀態。

**考慮過並否決的**：

| 候選 | 否決理由 |
|---|---|
| `check` | 在本專案已表示「這一個完成了」（ArchivedView、ChangeCard、SettingsModal、CopyNameButton 四處），且 tasks 畫面的勾選框是 17px，尺寸也撞 |
| `cog` / `settings-2` | `settings` 已是同一個側欄底部的 Settings；且齒輪是放射狀圓形，與點環同心相疊互相干擾 |
| `square-code`、`circle-dot`、`hexagon` | 方框或同心圓與環形成多層容器，互相打架 |
| `braces`、`code` | 對稱好看，但「這裡面是程式碼」與 App 實際顯示的 Markdown 文件對不上 |
| `asterisk` | 不宣告意思、與環同為放射狀構圖，是最接近的落選者 |

### D7 定案的數值

這些值全部來自打樣時的實測，不是估計：

| 項目 | 值 | 備註 |
|---|---|---|
| 狀態 | breathing | ring 模式：`spin: 0`、`faceOn: 1`、`ghostN: 0` |
| 設計尺寸 | 64 | 畫布 `64 × dpr`；CSS 呈現 50px |
| speed | 0.60 | 波紋繞一圈約 2.9 秒 |
| 記號盒子 | 50px | 環實際直徑 40.6px（盒子四周各留約 4.7px 透明邊），中間淨空 30.2px（＝環直徑的 74.4%） |
| 環上點的直徑 | 0.73–1.15px | 實測 CSS 直徑；0.48px 是 `rMin: 0.3` 換算後的下限，t=0 實際從未觸及 |
| terminal 看得到 | 10.6px | ＝淨空的 35% |
| terminal 圖框 | 16px | `stroke-width` 2.42，畫出來筆畫 1.60px |
| 品牌列高度 | 68.6px → 85px | wordmark 行盒 21 × 1.6 ＝ 33.6px，環超過它；以根字級 14px 計算，`py-5` ＝ 17.5px×2 |

## Risks / Trade-offs

**搬進來的程式碼與上游斷了連結** → 幾何那半一字不改，日後上游更新可以直接對檔比較；只有 painter 是我們自己的，範圍小到能用眼睛看完。

**迴圈在視窗可見時永遠在跑** → 畫布只有 128×128 device px、484 顆點，單幀成本極低；真正的成本是每秒喚醒六十次。目前接受；若日後測到影響，降頻是第一順位（speed 0.6 下 30fps 看不出差別），不是改用焦點當開關（見 D4）。

**品牌列加高 16.4px** → 側欄在較矮的視窗下可見專案數可能少一列。側欄寬度不變，該列寬度用掉 147px、內寬 189px 仍有餘裕。

**terminal 的 chevron 下臂與底線在格線上重疊 0.28px** → 刻意接受。打樣看過，重疊小到不糊，而且讓 `>` 與 `_` 讀成一個完整的提示符號而非兩筆分離的線；真實終端機的提示字元本來就是連著的。

**這是 App 第一個品牌記號，沒有前例可循** → 記號本身不承載任何狀態語意（spec 有明文），所以日後要換符號、換尺寸都只動這一個元件，不牽動其他 capability。

## Migration Plan

單向變更，無資料遷移、無 API 變動。回退＝還原 `AppSidebar.vue` 的品牌列兩行，並移除新增的元件與搬入檔。
