## Context

動機見 `proposal.md` 的 Why。這裡只記動手時需要的現狀與約束。

資料入口（`src/api/gateway.ts` 的 `gateway`）依執行形態分流，`desktopGateway` 以展開 `webGateway` 起手再逐一覆寫。目前 22 個方法覆寫了 21 個，唯一還沿用 web 那一份的是 `revealPath`。本張把它補上之後，展開那一行本身失去理由。

`src/api/desktop/shell.ts` 是外殼通道的薄層：只做型別與錯誤形狀的收束，不放任何商業規則。它對檔案通道的做法是直接呼叫外掛的指令（`plugin:fs|...`），不裝外掛的 JS binding 套件。

`src/markdown/render.ts` 的連結處理已經把「什麼算外部連結」定死在 `^(?:https?:|mailto:)` 這一個判定上：命中的輸出 `<a target="_blank" rel="noopener noreferrer">`，沒命中的輸出 `<span class="md-link-inert">`。`linkify` 是關的，所以純文字網址不會自己變成連結。

`src/components/MarkdownView.vue` 已有一個對整片內容的點擊委派，但它開頭就以「不是可勾選模式」整段退出，只服務 tasks 勾選。三個看內容的地方共用這個元件：change 詳情、Specs 全文、已歸檔詳情——後兩者永遠不是可勾選模式。

## Goals / Non-Goals

**Goals:**

- 兩條路（開啟檔案所在位置、開啟外部網址）在桌面形態下由外殼自持，不經本地 API server。
- 外部連結的開啟在兩個執行形態走同一條路徑，形態差異只出現在資料入口那一層。
- 開啟失敗有畫面上的回饋，不再是無聲的「點了沒事」。
- 桌面形態的資料入口不再借用 web 形態那一份。

**Non-Goals:**

- 不動 web 形態的既有實作（`server/api/reveal.post.ts`、`server/utils/reveal.ts`、`webGateway.revealPath`）。
- 不接「用預設程式開這個檔」。
- 不改連結與按鈕的任何視覺樣式。
- 不處理相對路徑連結（維持不可點）。

## Decisions

### D1. 外部連結的點擊由畫面這一側接住，不由外殼那一側接

`MarkdownView` 的點擊委派認出外部連結後擋掉預設行為，改呼叫資料入口的新方法；形態差異收斂在 `gateway.ts` 那一行。

**替代方案**：在 Rust 那側設一個跳轉處理，任何外部網址一律改交給系統瀏覽器，畫面端零改動。

**不選的理由**：三點。一是專案的既定做法是形態差異只出現在資料入口那一層，Rust 那側的做法把差異藏進外殼，前端測不到也讀不到。二是它沒有回傳值——開不起來時畫面上依然沒有任何回饋，那正是本張要修掉的毛病。三是 `revealPath` 本來就是「呼叫資料入口、依結果分流」的形狀，兩條路擺在一起才對稱。

### D2. 兩個形態一律接住，不為修飾鍵開特例

點擊處理不看 `metaKey`／`ctrlKey`。在瀏覽器裡跑的開發通路，Cmd／Ctrl＋點從背景分頁變成前景分頁。

**替代方案**：按著修飾鍵時不擋預設行為，交回執行環境。

**不選的理由**：桌面視窗形態不處理開新視窗，「交回執行環境」在那裡等於什麼都不做——等於在交付形態裡留一條點了沒反應的路，而那是本張要修掉的東西。為了開發通路的一個次要手勢，換來兩個形態行為不一致，不划算。

中鍵與右鍵選單不受影響：中鍵在現代瀏覽器不觸發 `click`，右鍵選單沒有被攔。`href` 保留，所以停留看得到網址、右鍵複製連結仍可用。

### D3. 新方法回傳成功／失敗兩態，不設「此環境不支援」

`RevealOutcome` 有三態是因為 web 形態的 `open -R` 只在 macOS 成立，「這個平台辦不到」是一個答得出來的真實答案。開啟外部網址沒有這個問題：web 形態一定開得了新分頁，桌面形態具備外殼通道。沒有來源的狀態不編出來。

同理，`EnvironmentDiagnostics` 的「能不能開啟所在位置」由三態（是／否／未知）收斂為兩態。先例是 T4a 對「檔案變動通知」做的同一件事。

`RevealOutcome` 本身維持三態不動：web 形態在非 macOS 仍會回「這個平台辦不到」。

### D4. `render.ts` 的 `target="_blank"` 與 `rel` 保留

接住那段若失效（改壞、事件沒綁上），留著它是開新分頁、App 狀態還在；拿掉則會在同一個畫面導航走，整個 App 被換掉。壞掉時的代價不對稱，所以留。

在桌面視窗形態下這兩個屬性本來就沒有作用，留著不產生任何行為。

### D5. 照檔案通道的先例直接呼叫外掛的指令，不自寫 Rust 包裝

T4b 之所以自寫 Rust 包裝，是因為資料夾對話框外掛的前端指令會在 `openspec/` 驗證之前就把選定資料夾放進檔案可讀範圍，而那個範圍只能加不能減。這個外掛沒有同等的已知行為：開啟網址不碰檔案範圍，在檔案管理器中選取項目依外掛的權限表是「不吃預先設定的範圍」的指令。

**但這是本張唯一需要動手前實測的假設**，不能從 T4b 的結論推過來。

**驗證方式變更**：`tasks.md` 原訂以桌面形態啟動、在開發者工具裡呼叫指令實測。這在自動化實作環境裡做不到——Tauri webview 的開發者工具需要人手操作，且專案 `CLAUDE.md` 明訂已有一份 vite 在跑時不得在同一專案另起第二份（`node_modules/.vite` 相依快取共用，第二份啟動可能把正在跑的那份寫壞）。改以原始碼與外掛自帶的權限定義查證同一個假設，結論等價：程式碼路徑若完全不觸碰檔案可讀範圍的物件，執行期實測也只會得到相同答案。

**查證證據**（crate: `tauri-plugin-opener` 2.5.5，即 `src-tauri/Cargo.lock` 實際解析到的版本，`cargo fetch` 後之 registry 原始碼，路徑為 `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-plugin-opener-2.5.5/`）：

1. **暴露的指令本身不吃任何 scope 參數。** `src/commands.rs` 第 73-76 行：
   ```rust
   #[tauri::command]
   pub async fn reveal_item_in_dir(paths: Vec<PathBuf>) -> crate::Result<()> {
       crate::reveal_items_in_dir(&paths)
   }
   ```
   對照同檔的 `open_url`／`open_path`（第 14-70 行）都吃 `CommandScope<Entry>` 與 `GlobalScope<Entry>` 兩個 extractor 並呼叫 `Scope::is_url_allowed`／`is_path_allowed` 做放行判斷；`reveal_item_in_dir` 完全沒有這兩個參數，函式本體也不建立任何 `Scope`。

2. **底層實作直接呼叫作業系統 API，不經任何 Tauri scope。** `src/reveal_item_in_dir.rs`：路徑先以 `std::fs::canonicalize`（或 Windows 版 `absolute_and_check_exists`）解出真實路徑，再依平台呼叫 `imp::reveal_items_in_dir`——macOS 呼叫 `NSWorkspace::activateFileViewerSelectingURLs`（第 262-277 行一帶）、Windows 呼叫 `SHOpenFolderAndSelectItems`、Linux 走 D-Bus 的 `org.freedesktop.FileManager1`／`org.freedesktop.portal.OpenURI`。全檔搜尋 `fs::Scope`／`allow_directory`／`allow_file`／`FsExt`／`fs_scope` 零命中。

3. **`open_path` 用到的 scope 檢查也只是外掛自己 ACL scope 的一次性投影，不是 fs 外掛的常駐 scope。** `src/scope.rs` 第 126-140 行的 `is_path_allowed` 雖然建了一個 `tauri::fs::Scope::new(...)`，但傳入的 `allow`／`deny` 來自 `self.allowed`／`self.denied`（也就是呼叫端傳進來的 opener 外掛自己的 ACL scope entries），是每次呼叫當場現組的臨時物件、僅用於 `is_allowed(path)` 這一次布林判斷，不讀寫 `tauri_plugin_fs` 那個常駐、只能加不能減的 scope 物件；而且這條路徑本來就與 `reveal_item_in_dir` 無關（它是 `open_path` 專用，本張未放行 `opener:allow-open-path`）。

4. **crate 對 `tauri-plugin-fs` 零依賴。** `Cargo.toml`（registry 正規化版）的 `[dependencies]` 清單裡沒有 `tauri-plugin-fs`，證實這個外掛在編譯期就不具備碰觸檔案外掛 scope 的能力。

5. **外掛自帶的權限定義檔也如此宣告。** `permissions/autogenerated/commands/reveal_item_in_dir.toml`：
   ```toml
   [[permission]]
   identifier = "allow-reveal-item-in-dir"
   description = "Enables the reveal_item_in_dir command without any pre-configured scope."
   ```
   「without any pre-configured scope」是外掛作者自己的定性——這個指令沒有 scope 概念，不是「scope 留空即全放行」。

**結論：假設成立**，兩份證據（指令簽章不吃 scope＋底層實作不碰任何 fs scope API）方向一致，指向「不會擴大檔案可讀範圍」。照 D5 原定做法繼續，不退回 T4b。

### D6. 權限用外掛現成的預設網址集，不自列清單

外掛提供一項涵蓋 mailto／tel／https／http 的預設網址集權限。渲染層認定的外部連結是 https／http／mailto，兩者的差別只有 tel——而 `linkify` 是關的、`tel:` 也不在渲染層的外部連結判定裡，所以 `tel:` 網址永遠到不了通道。自列清單換不到任何實質收窄，反而多一份要跟著渲染層同步的設定。

真正的收窄在渲染層：`^(?:https?:|mailto:)` 那一個判定就是通道的入口守衛，它擋不住的東西根本不會被畫成可點的連結。

**補記（`file:`／`javascript:`／`data:`／`vbscript:` 的實際長相）**：這四個 scheme 在到達 `applyLinkPolicy` 之前就先命中 markdown-it 內建的 `BAD_PROTO_RE`，link token 根本沒有解析出來，輸出是未解析的方括號原文（例如 `<p>[a](file:///etc/passwd)</p>`），不是 `.md-link-inert`。`specs/artifact-view/spec.md` 的 scenario 說這兩者「渲染為非互動樣式」，字面上仍成立——原文確實不可互動、點了沒有導航——但實際渲染結果與 `.md-link-inert`（相對路徑連結、`tel:` 等真正流到 `applyLinkPolicy` 才被擋下的 scheme）不是同一種長相，不要把這句話當成「守衛只有一層、且輸出永遠是 `.md-link-inert`」的依據。

**補記（守衛層數）**：`MarkdownView.vue` 的 `openLink()` 交出去前另外把 scheme 正規化成小寫、重新比對允許清單（見該檔 `normalizeAllowedUrl`）——這是修 render.ts 的 `/i` 大小寫判定與桌面形態 Rust 端 `glob::Pattern` 大小寫敏感比對之間落差時補上的第二層。至此通道實際是兩層守衛：渲染層（`applyLinkPolicy`，決定畫不畫成 `<a>`）＋畫面端（scheme 大小寫正規化＋允許清單重比對，決定要不要真的呼叫資料入口），不是單一入口守衛。

**實作附記（對 `tasks.md` 1.3 字面的訂正）**：`tasks.md` 1.3 的驗證句原寫「該檔案本張新增的只有這兩項」，字面上只點名 `opener:allow-reveal-item-in-dir` 與外掛的預設網址集權限兩項。但 `opener:allow-default-urls`（`permissions/allow-default-urls.toml`）只帶 `permission.scope.allow` 的網址清單，沒有 `commands.allow`；而 Tauri 的 ACL 是否放行一個指令的 IPC 呼叫，只看有沒有任一已授權權限的 `commands.allow` 含該指令名（見 `tauri` 2.11.5 原始碼 `src/ipc/authority.rs` 第 297-320 行 `has_permissions_allowing_command`，只檢查 `permission.commands.allow.contains(&command.into())`）——scope-only 的權限不會把指令加進放行清單。也就是說單放 `allow-default-urls` 並不會讓 `open_url` 這個指令本身可被呼叫，之後 2.2／4.1 一旦真的呼叫 `plugin:opener|open_url` 會直接被 IPC 層拒絕，與 scope 內容無關。外掛自己的 `default` 權限集（`permissions/default.toml`）也印證同一組合：`allow-open-url` ＋ `allow-reveal-item-in-dir` ＋ `allow-default-urls` 三項合起來才是完整可用的「預設網址集」。這與既有 `fs:allow-read-text-file`＋`fs:scope` 的搭配是同一種形狀（指令放行與 scope 收窄分兩個權限），屬於補齊同一個既定模式的筆誤級落差、對應方式唯一，故本張實際新增 `opener:allow-open-url` 與 `opener:allow-default-urls` 兩項（連同 1.1 的 reveal 共三項），未依原句只加一項。

### D7. 桌面形態的開啟位置能力一律答「可以」

外掛在檔案管理器中選取項目的指令三個平台都有實作，桌面形態沒有 web 形態那種「這個指令只有 macOS 有」的限制。所以它不做平台分支，一律答可以；開不起來的情形落在「失敗」而不是「這個平台辦不到」。

### D8. 新模組放一個檔，兩條路同住

新增 `src/api/desktop/opener.ts`，同時放「開啟所在位置」與「開啟外部網址」。沿用一個領域一個檔的既有做法（`folder-picker.ts`、`watch.ts`、`park.ts`），兩條路共用同一個外掛，是同一個領域。

`shell.ts` 新增兩個對應的出口，各自只做型別與錯誤形狀的收束。

### D9. 「診斷中的某一項可能尚無通道可問」那一段規則留著

本張之後，診斷的每一項都答得出明確的值，那段規則沒有作用中的對象。仍然留著：它是對「未來新增診斷項時該怎麼回答」的約束，不是對某個現存項的描述。真正拿掉的是那條以桌面形態為前提、已不可能成立的 scenario。

### D10. `getHealth` 移除

`src/api/index.ts` 的 `getHealth` 繞過資料入口直接打本地 API server，功能早已由環境診斷取代，目前沒有任何呼叫端。ROADMAP 把它列為 gateway 移植的收尾項，而本張是移植的最後一張。

## Risks / Trade-offs

- **外掛的指令可能擴大檔案可讀範圍（D5 的假設若為假）** → 動手第一步先實測；測出會擴大就退回 T4b 的自寫 Rust 做法。這個順序讓假設在寫任何前端程式之前就有答案，不會做完才發現要重來。
- **web 形態開新分頁被瀏覽器擋下** → 開新分頁必須是該方法內的第一件事，不能排在任何等待之後。等待一旦插在點擊與開窗之間，瀏覽器就不再把它當成使用者按出來的，會直接擋掉。這一點要有測試釘住。
- **點擊委派要在唯讀模式下也運作** → 目前那道「不是可勾選模式就整段退出」的守衛必須改成只圍住勾選那一段。改錯會讓 Specs 全文與已歸檔詳情裡的連結仍然點不動——而那兩處永遠是唯讀模式，是最容易漏測的地方。三個使用處都要驗到。
- **Cmd＋點在瀏覽器裡的行為改變**（背景分頁 → 前景分頁）→ 已知且接受，見 D2。
- **web 形態點 mailto 可能留下一個空白分頁** → 刻意不處理，見 `proposal.md` 的「已知會留下的粗糙處」。這不是遺漏。
- **`canReveal` 由三態收斂為兩態會動到型別** → 型別收窄會讓所有讀它的地方在編譯期被點名，包含 `SettingsModal.vue` 裡那句「這個形態還沒有這個通道」的分支。這是好事：沒有漏網的可能。

## Migration Plan

不涉及資料搬遷。行為的切換點只有一個：`desktopGateway` 補上兩個方法、拿掉展開 `webGateway` 那一行。回退方式是把那一行加回去並移除覆寫。

`src-tauri` 的相依與權限是新增，不改既有項；權限清單只能加不能減的約束在本張不構成風險——新增的兩項都不是檔案可讀範圍。
