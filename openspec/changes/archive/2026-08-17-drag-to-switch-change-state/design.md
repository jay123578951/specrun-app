## Context

見 proposal.md — Why。這裡只處理實作路線與其取捨。

四個既存約束決定了大部分決策：

1. **`tokens.css` 全域禁用 `box-shadow`**，唯一例外是浮層（dropdown、toast）用的 `--sr-shadow-overlay`；層次一律靠 surface 色階＋1px 邊框。拖曳的「浮起」感在絕大多數實作裡完全依賴陰影，這條需要正面裁決。
2. **`interactions.css` 的 `.card-lift:active { transform: none }`** 是刻意的按壓感（把 hover 抬升壓回去）。拖曳啟動必經 `:active`，兩者會直接打架。
3. **`loadSilently()` 會在 watcher 通知時整批替換 `changes.value`**，且刻意不打任何進行中旗標。樂觀移動期間這件事隨時可能發生。
4. **群組內順序由資料層決定**（`Active` 沿用 CLI 回傳順序、`Parked` 由 `normalizeParkedList` 排序），本 change 不引入手動排序。這一條反過來大幅簡化了落點模型。

`park()`／`unpark()` 與其失敗提示、`parkAvailable`／`parkReason` 降級旗標都已存在於 `src/stores/changes.ts`，本 change 不新增任何 gateway 呼叫。

**順序依賴**：本 change 的原位凹槽需要量測卡片實際高度，前提是卡片高度不一致——那是 `show-why-summary-on-cards` 引入的。該 change SHALL 先實作並 archive；本 change 的凹槽實作不得假設固定高度。

## Goals / Non-Goals

**Goals:**
- 拖曳的落點語意與實際結果完全一致：不承諾系統做不到的事（群組內位置）。
- 零版面位移的目的地標示——標示出現與消失都不得推動任何卡片。
- 樂觀移動能在 watcher 靜默重載的干擾下存活，不閃動、不殘留。
- 不引入執行期依賴。

**Non-Goals:**
- 不做群組內重排、不做排序持久化（proposal 已列非目標；本 design 也不預留其擴充點——真要做時落點模型會整體改變，預留只會綁手）。
- 不做拖到邊緣的自動捲動（改記 ROADMAP 觀察項）。
- 不為觸控裝置優化（桌面 App；統一走 Pointer Events 即可，不另做手勢處理）。
- 不新增鍵盤重排模型：狀態切換的鍵盤等價路徑就是既有的 Park／Restore 按鈕，spec 已將其立為不可移除。

## Decisions

### D1: 自製 Pointer Events，不用 HTML5 Drag and Drop、不引入拖曳庫

**選擇**：`pointerdown` → `setPointerCapture` → `pointermove` / `pointerup` 自行管理拖曳狀態。

**否決 — HTML5 Drag and Drop API**：它的原生 drag image 無法客製到本專案需要的程度（scale、陰影、圓角都由瀏覽器決定），且 WKWebView（Tauri 的 webview，ROADMAP 已列為已知坑）的 drag image 表現與 Chromium 差異大。`dragover` 的事件模型也讓「拿起即標示目的地」變得彆扭——它假設目的地要靠 hover 發現。

**否決 — 引入 Sortable.js／vuedraggable／motion**：這些庫的核心價值是 reorder 與 FLIP 補間。本 change 明確不做 reorder，剩下要用的只有「跟著指標移動」——那是十幾行的事。引入一個執行期依賴換取用不到的功能，且要另外驗 WKWebView 相容性，不成比例。

**代價**：邊界情況要自己處理（指標離開視窗、拖曳中卡片被 watcher 重載移除）。`setPointerCapture` 覆蓋掉大部分——它保證後續 pointer 事件都送到同一個元素，即使指標移出視窗。

### D2: 落點粒度＝群組級，且拖曳啟動即確定目的地

**選擇**：不做行間插入指示線，改為整個目的地群組標示；且因只有兩個群組、群組內不重排，目的地在 `pointerdown` 進入拖曳的那一刻就唯一確定，立即標示。

**理由**：這是 D-約束 4 的直接推論。若畫行間插入線，就承諾了「卡片會落在這兩張之間」——但落地後排序由資料層重算，卡片會跳到別的位置。給出假承諾比不給提示更糟。

「拿起即標示」則順帶解決了拖曳最常見的迷失問題（不知道能拖去哪）：使用者不必移動探索，一按下就看到唯一的去處。

**替代方案 — 等指標移入目的地才標示**：符合多數拖曳實作的慣例，但在「目的地本來就唯一」的情境下純屬多一道摸索。否決。

### D3: 目的地標示用 `outline`，不用 `border` 或 `padding`

**選擇**：目的地群組容器加 `outline: 1px dashed` ＋ `outline-offset`，配極淡底色。

**理由**：群組容器目前是裸的 `space-y-3`。`border` 會佔據佈局空間、把卡片往內推，標示出現的瞬間整群卡片跳一下——spec 已把「標示不造成版面位移」立為 scenario。`outline` 不參與佈局，`outline-offset` 讓框線離開卡片邊緣而不需要 padding。

框線用 `--sr-line` 而非 `--sr-accent`：`accent/25` 已經是「詳情開啟中的那張卡」的既有語意（`ChangeCard.vue`），拖曳中若同時出現兩種 accent 底，兩個狀態會分不清。底色用極淡的 accent 就夠表達「這一區活了」。

### D4: 空群組的內容區塊自身即標示載體，不疊加群組標示

**選擇**：群組為空時，只讓該群組的空內容區塊自己從低強度切到高強度；有卡片時才用 D3 的群組 outline。兩者互斥。

**這條適用於兩種空內容區塊，不只 Parked 的落點槽**：`StateNotice.vue` 本身是 `border border-line bg-surface`，Active 空群組作為落點時同樣不能外加 outline，否則就是實線框外面再套虛線框。它的標示改由自己的 border 從實線切為 dashed、提亮並加淡底來表達。

**理由**：空內容區塊本身都已具備邊框，若再套上群組 outline，畫面會出現兩個嵌套的框——使用者無從判斷哪一個才是落點。spec 已將「單層標示」對兩種區塊各立一條 scenario。

三態的強度階梯只用透明度與一層極淡底色表達，全在既有 token 內，不新增顏色：常駐為低對比（框線與文字都降透明度）、拖曳中為全對比＋淡底、不可用為灰化。文案在常駐與拖曳中之間切換（陳述句 → 放手動作語意），因為「放手就成立」的確認值得那一次文字變動。

### D5: 兩群組皆空時 Parked 整段不顯示

**選擇**：「兩群組恆常呈現」的前提是清單中存在至少一張卡片。兩群組皆空時 Parked 整段不顯示，主區只留 Active 的引導空狀態。

**理由**：恆常顯示的唯一理由是拖曳需要落點。兩群組皆空＝沒有任何卡片可拖＝落點無作用，此時顯示落點區塊是純粹的噪音，而且是首次開啟新專案就會看到的第一屏。這與 `ChangeList.vue` 既有的 `noProject` 處理精神一致——「還沒開始」不該用滿版的功能性 UI 迎接使用者。

**連帶後果**：Active 空狀態的文案必須隨是否存在 parked change 切換。沒有 parked 時仍寫「可自 Parked 拖回」是無效指引——那個群組當下根本不存在。spec 已為兩種文案各立 scenario。

**代價**：規格多一條例外、實作多一個條件分支。換到的是新專案首屏乾淨。此例外的邊界明確（卡片總數為零），不是模糊的啟發式判斷。

### D6: 拖曳中的卡片視為浮層，適用 `--sr-shadow-overlay`

**選擇**：拖曳中的卡片使用 `--sr-shadow-overlay`，並輔以 `scale(1.02)`。

**理由**：`tokens.css` 的禁令針對的是「用陰影做常態層次」——那會讓整個介面浮起來、失去它刻意的平整感。拖曳中的卡片脫離文件流、跟著指標飄在其他內容之上，比 toast 更符合「浮層」的定義。這是既有例外的適用，不是新增例外。

若不用陰影，只剩 `scale` 能表達抬起，而 1.02 的縮放幅度小到幾乎讀不出來——卡片會像卡在紙面上滑動而非被拿起來。

**不採用的細節**：不做旋轉（風格層「圓角克制」的克制調性，歪斜的卡片偏玩具感）；border 顏色不變（理由同 D3）。

### D7: 拖曳啟動時移除 `card-lift`

**選擇**：進入拖曳狀態的卡片動態移除 `card-lift` class。

**理由**：`.card-lift:active { transform: none }` 的優先級會與拖曳的 `transform: translate(...) scale(1.02)` 衝突，且拖曳全程指標都處於按下狀態。不移除的話卡片會在拿起瞬間先被壓回原位再跳起來。這是既有樣式的必然衝突，不是可調參數。

### D8: 樂觀狀態獨立成一層，不改寫 `changes.value`

**選擇**：store 新增一個樂觀搬移描述（對象名稱與方向），渲染時把它套在 `changes` / `parked` 之上算出顯示清單；`changes.value` 與 `parked.value` 永遠只承載伺服端的真實資料。

**理由**：這是 D-約束 3 的直接後果。`loadSilently()` 在 watcher 通知時整批替換 `changes.value` 且不打旗標——若樂觀移動是靠直接改陣列實現，一次不相關的檔案存檔就會讓卡片閃回原群組再跳回去。把樂觀狀態放在獨立一層，重載換掉底層資料時，套用結果不受影響。

操作結束（成功或失敗）時清掉該層：成功後由 `load()` 的實際結果接手，失敗則觸發回滾動畫後清除。既有的 `parkPending` 是「同時只允許一個操作」的閘門，語意與樂觀層重疊，實作時合併為同一組狀態，不要並存兩個真值。

**替代方案 — 樂觀移動直接改陣列、並在操作期間暫停 `loadSilently`**：需要在 watcher 路徑上加旗標判斷，把兩個原本無關的機制耦合起來，且暫停期間的變動會被漏掉。否決。

### D9: 原位凹槽高度以實測值設定

**選擇**：`pointerdown` 進入拖曳時以 `getBoundingClientRect()` 取被拖卡片高度，寫入凹槽的 inline style。

**理由**：`show-why-summary-on-cards` 之後卡片高度隨摘錄有無而異，凹槽寫死高度會讓下方卡片在拖起瞬間跳動。量測時機必須在卡片脫離文件流之前。

凹槽外觀用 `bg-bg`（比 `surface` 更深，讀起來是挖穿卡片層露出視窗底）＋ 1px dashed `line`，與真實卡片明確可分。

### D10: 純 CSS transition，spring 值只作手感參照

**選擇**：不引入動畫庫；`interior.dev` 的 `{ stiffness: 520, damping: 34, mass: 0.45 }` 不轉譯成等效 cubic-bezier，只取其「快速起步、幾乎不回彈」的性格，實作沿用既有的 `--sr-ease-out`（進出場）與 `--sr-ease-in-out`（畫面內移動）。返回原位用 `--sr-ease-in-out` 250ms——比進場動畫長，讓「沒去成」看得見。

**理由**：需要補間的只有兩處（返回原位、落地後的重排），且 `ChangeList.vue` 既有的 `TransitionGroup` 已在處理重排。拖曳跟隨本身是逐幀對映指標位置，沒有補間可言，spring 在這裡無處施力。為兩個 transition 引入 physics runtime 不成比例。

## Risks / Trade-offs

- **拖曳中的卡片被 watcher 重載移除**（外部工具剛好刪掉那個 change）→ 拖曳狀態以 change 名稱為鍵，套用樂觀層時找不到對象即中止拖曳、釋放 pointer capture，不顯示錯誤。實際狀態以重新列舉為準，與既有紀律一致。
- **`setPointerCapture` 在 WKWebView 的行為與 Chromium 有差異** → Pointer Events 是 Safari 長期支援的標準 API，風險主要在細節（capture 期間的 `:hover` 狀態）。web 開發階段先驗 Chromium，M4 套 Tauri 時本來就有整體驗證關卡，屆時一併確認；不因此改變實作路線。
- **樂觀移動讓「清單即真實狀態」出現短暫例外** → 這是 spec 層的自覺讓步（`park-mechanism`「操作失敗呈現」已改為要求進行中標示）。標示必須真的可辨識，否則就是在騙人；實作時進行中標示的強度需人工驗收。
- **兩群組恆常顯示會讓畫面多出常駐區塊** → 這正是當初 P1 決定隱藏空群組的理由（「一行沒有內容的噪音」）。D5 已把最糟的一屏（全新專案、兩群組皆空）排除在外，剩下的暴露面是「有 active 但無 parked」這個常態——以低強度常駐落點區塊緩解，但仍是本 change 主要的視覺風險，需在驗收時實看（tasks 7.9）：若常駐提示確實過吵，退路是把它降到只有標題與數量、落點區塊改為拖曳中才出現——代價是首次使用發現不了拖曳。
- **群組呈現條件從一個判斷變成兩個** → `showParked` 由「有 parked」改為「有任何卡片」，另加雙空例外。條件本身仍是純粹的計數比較，但兩個計數在載入期間會先後到齊（`load()` 併發發出 active 與 parked 兩路請求），首幀可能出現「active 已回、parked 未回」的中間態而讓 Parked 群組閃現。實作時條件需與既有的 `firstLoadPending`／skeleton 分支一致對待，不得在 skeleton 期間就依半份資料決定群組是否顯示。
- **卡片整張可拖與點擊開詳情共用同一次指標互動** → 以位移門檻分流（5px；小於一般誤觸幅度、大於手抖）。門檻內放開走既有點擊路徑。風險在門檻附近的模糊區——選 5px 是因為卡片是大目標、使用者不需精準定位就能點中，可容忍略大的門檻。
- **拖曳中詳情面板開著** → 面板是右側覆蓋層，露出區的卡片仍可拖。卡片浮起後可能移到面板下方；不特別處理（放手若不在合法目的地即取消），也不在拖曳時關閉面板——那會讓使用者失去正在讀的內容。
