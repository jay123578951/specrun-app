## Context

動機見 `proposal.md` 的 Why。這裡只寫實作要面對的現況。

本 change 的範圍是**用排除法定義**的：`make-comments-self-contained` 逐條判定並改寫完乙丙兩類之後，`src/` 底下剩下的所有規格文件引用。所以開工的第一件事是重跑那個 change 的掃描指令確認它真的清乾淨了，而不是照一份名單做。

剩下的引用不是同一種形狀。實際去看，有三種：

```
  甲-1  整個括號就是出處，括號刪掉、句號留著        約 160 處
        「…parked 來自現場解析（design D4）」
                              +--- 整括號刪 ---+

  甲-2  括號裡除了出處還有真內容，要拆不能整刪        40 處
        「（與 normalize 同一個方向，design D1）」
          +--- 這半要留 ---+ +-- 這半刪 --+

        「（design D3、orb-color.test.ts）」
                     +-- 刪 --+ +- 這是程式碼引用，要留 -+

        「（design D7：同畫面變形無 URL 需求，不引入 router）」
          +- 刪引用頭 -+ +------- 冒號後面是理由，要留 -------+

  代號   換成它實際指的事，不是刪掉                   14 處
        「web 與 M4 Tauri 版共用」-> 「web 與日後的 Tauri 版共用」
```

甲-2 那 40 處是這個 change 真正的風險所在。整括號刪掉最省事，但會連帶刪掉三種該留的東西：括號裡的真內容、指向程式碼的引用、以及冒號後面本來就是理由的那半句。

## Goals / Non-Goals

**Goals:**

- `src/` 底下不再有任何指向規格文件的引用——`grep -rnE "design D[0-9]|spec [a-z-]{4,}" src/` 結果為空。
- 句子的資訊量不減少：刪掉的只有出處，真內容一律留下。

**Non-Goals:**

- 不改寫任何句子的措辭。這個 change 只做刪除與代號替換；需要重寫句子的都屬於前一個 change 的乙丙類，不在這裡處理。
- 不動 `design.md`、`openspec/specs/`、`docs/` 等文件本身。
- 不動任何 code 邏輯、變數名、格式。
- 不建立規範檔——規範層由 kit 統一修。

## Decisions

### E1 開工前先確認前一個 change 已清乾淨

**選擇**：第一件事是重跑 `make-comments-self-contained` 的兩條判定掃描。丙類掃描（引用後面接「的」「：」「實測」「定案」）必須為空；乙類的 13 處候選必須都有判定結果。任一條不成立就停下來，不往下做。

**理由**：本 change 的範圍是排除法定出來的。前一個 change 沒清乾淨就往下刪，會把「只寫規則沒寫理由」的註解當成一般出處刪掉——規則留著、理由沒了，比現在更糟。

### E2 這個 change 只刪不改寫，句子一字不動

**選擇**：刪掉出處之後，句子其餘部分完全不動，包括措辭、標點與換行。刪完發現句子讀不通，代表那一處當初分類分錯了，退回前一個 change 的乙丙判準處理，不要在這裡順手重寫。

**理由**：兩百處的 diff 要能靠機械檢查。只刪不改的話，每一行的新增與刪除之間只差一個括號，人工掃過就看得出對不對；一旦允許順手改措辭，就得逐句讀，兩百處讀不完。

### E3 括號要拆，不要整個刪

**選擇**：括號裡除了出處還有別的內容時，只刪出處那一段，保留括號與其餘內容。三種形狀各自的處理：

| 形狀 | 例 | 改成 |
|------|-----|------|
| 出處跟在真內容後面 | `（與 normalize 同一個方向，design D1）` | `（與 normalize 同一個方向）` |
| 出處跟程式碼引用並列 | `（design D3、orb-color.test.ts）` | `（見 orb-color.test.ts）` |
| 出處後面接冒號展開 | `（design D7：同畫面變形無 URL 需求，不引入 router）` | `（同畫面變形無 URL 需求，不引入 router）` |

**理由**：第二種若整括號刪掉，會刪掉一個指向程式碼的引用——那是使用者明確要保留的。第三種的冒號後面本來就是理由，整括號刪掉等於把理由丟了，反而製造出新的乙類。

**考慮過的其他做法**：一律整括號刪。省事，但上表後兩種會出錯，而且錯得看不出來——句子仍然通順，只是少了資訊。

### E4 代號換成它實際指的事，不留代號、也不改成新的引用

**選擇**：`M4`／`M3`／`C3`／`C4`／`C5`／`T1`／`T2` 一律換成白話。不寫成「見 ROADMAP.md」這種新引用。

**理由**：換成新引用只是把一種要翻文件的寫法換成另一種。

**附帶發現**：`M4 Tauri 版` 與 `T1`／`T2` 是兩套不同的代號在講同一件事（Tauri 化的階段），同一個 codebase 裡並存，讀的人分不出 `M4` 等於 `T1` 還是 `T2`。改寫時統一用白話描述，這個歧義一併消失。

### E5 實作順序硬性排在 `make-comments-self-contained` 之後

理由見 E1。兩個 change 同時存在於 `openspec/changes/`，但本 change 要等前一個人工驗收通過才開始實作。

## Risks / Trade-offs

- **整括號誤刪**（甲-2 那 40 處）→ 這 40 處單獨列一章先做，逐條核對，不混進純刪除的批次裡；收尾時檢查 `git diff` 的刪除行裡不得出現非出處內容。
- **標點斷裂**（刪掉括號後留下孤立的句號、頓號、或連續標點）→ 收尾時對改動檔搜尋連續標點與行尾孤立標點。
- **兩百處的 diff 沒人讀得完** → 驗收改用機械檢查：每一對增刪行的差只能是出處字串，以及全 repo 掃描為空。人工只看甲-2 那 40 處與代號那 14 處。
- **範圍隨前一個 change 的判定結果浮動** → 接受。本 change 不維護固定名單，開工時現掃。
- **`BrandMark.vue`、`orb-color.ts` 等檔可能同時被 `add-orb-logo` 動到** → 開工前確認工作區乾淨。

## Migration Plan

純註解改動，無部署與回滾議題。

做完之後，`src/` 底下就只剩下指向程式碼自己的引用（`見 settleMove`、`依 projects.ts 慣例`、`機制見 interactions.css`）。規範層——要求日後寫 code 時註解必須自足——不在這兩個 change 裡，已記進跨專案回饋收件匣由 kit 統一修；在那之前新寫的 code 沒有規範可讀，可能再長出新的引用。
