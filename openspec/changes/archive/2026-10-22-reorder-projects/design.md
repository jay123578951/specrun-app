# Design

## Context

- 專案順序就是設定檔 `projects` 陣列的順序。桌面版存在 `src/api/desktop/projects.ts` 的記憶體設定裡，開發用 API 存在 `server/utils/project-state.ts`。兩邊組清單時都照這個陣列排，暫時項另外插在最前面。
- 兩邊的寫檔都會吞掉失敗：桌面版是 `persistAndNotify`，開發用 API 是 `persist`。理由是加入、移除、切換時，設定檔寫不進去也不該讓操作失敗。
- `src/stores/projects.ts` 的加入、移除、切換都走 `mutate()`：先把 `busy` 設成 true，呼叫 gateway，收下回傳的整份清單。`busy` 為 true 時，側欄的非目前專案會變成 disabled，畫面會變淡。
- `ChangeCard.vue` 已經有一套自己寫的 pointer 拖曳：5px 門檻、pointer capture、拖過就吞掉接下來的 click，指標被系統收走時取消拖曳。

## Goals / Non-Goals

**Goals:**
- 一個 gateway 動作同時服務拖曳與鍵盤兩種排序。
- 排序的存檔不讓側欄閃一下變淡，也不跟切換、加入、移除互相蓋掉結果。

**Non-Goals:**
- 拖到清單可見範圍邊緣時自動捲動。清單上限是收合門檻 12 項，展開後要捲動才看得到全部的情況很少。
- 拖曳中用滾輪捲動清單時重新計算落點。
- 螢幕閱讀器的移動結果朗讀（aria-live）。
- 觸控裝置的長按拖曳。

## Decisions

### 1. gateway 動作傳整份順序：`reorderProjects(paths: string[])`

呼叫端傳出調整後的完整路徑陣列，不含暫時項。後端先確認這份陣列和目前設定的 `projects` 是同一組路徑，只有順序不同。不是同一組就回 `{ ok: false }`，代表使用者調整時看到的清單已經過時。

考慮過的另一種做法是 `moveProject(path, toIndex)`。它要靠後端推算「移到第幾格」，清單在中途變過時，結果會落在使用者沒預期的位置。傳整份順序時，後端只要比對一次就知道清單有沒有變。重送同一份也不會出錯。

### 2. 排序的寫檔失敗要回報，其他動作維持靜默

使用者的決定是「存檔失敗就彈回並跳 toast」。排序這條路直接呼叫寫檔，不經過會吞錯誤的包裝：

- 寫檔失敗時，把記憶體裡的 `projects` 還原成呼叫前的順序，再回 `{ ok: false }`。
- 加入、移除、切換照舊靜默降級，不在這次改動範圍。

理由：加入、移除、切換在畫面上有其他回饋，例如目前專案換了。排序唯一的成果就是「順序被記住」。順序沒存成功卻不說，使用者下次開 App 才會發現順序跑掉。

### 3. store 的排序不走 `mutate()`，畫面先換順序

`reorder(paths)` 的流程：

1. 立刻把 `projects` 換成新順序。
2. 呼叫 gateway。
3. 成功時記下「最後一次存成功的順序」，不收回傳的清單。
4. 失敗時照「最後一次存成功的順序」重排現有的項目，再跳 toast。

不走 `mutate()` 有兩個原因：

- `mutate()` 會把 `busy` 設成 true，存檔那一瞬間其他專案會全部變淡再變回來。
- 回傳的清單是存檔當下的快照。如果套用它，可能會蓋掉更晚發生的狀態。

存檔要排隊。同時間只有一個排序在存，存檔途中又排了一次（例如連按 Alt+↓），就等目前這次存完，再送最新的順序，中間的順序直接略過。

`mutate()` 開始前要先等排序存完。這樣一來，加入或移除不會在排序存到一半時插進來，排序的後端比對也就不會因為這樣失敗。反方向不用處理：`busy` 為 true 時本來就不能排序。

失敗時的重排只動順序，保留各項目當下的 `current` 與徽章。

### 4. 拖曳沿用 ChangeCard 的寫法，只能上下移動

`ProjectSwitcher.vue` 自己處理 pointer 事件，不引入拖曳套件。流程：

1. pointerdown 時記下起點，並設 pointer capture。按在 ✕ 等按鈕上時直接略過。
2. 移動超過 5px 才進入拖曳。進入的當下量好每一列的位置和高度。
3. 被拖的那一列只沿垂直方向跟著指標移動。
4. 依指標位置跨過哪幾列的中線，算出要落在第幾格。落點和原位之間的列各位移一列的距離，讓出空位。
5. 放開時，用落點算出新陣列交給 `store.reorder()`，並吞掉接下來的 click。
6. pointercancel 時取消拖曳，各列回到原位，不存檔。

拖曳中在清單外層加一個狀態 class，把 ✕ 藏起來。讓位的位移加短 transition，數值照 ui-motion skill。使用者設定減少動態時，不加 transition。

### 5. 鍵盤：在專案按鈕上處理 Alt+↑／↓

專案按鈕的 keydown 收到 `Alt+ArrowUp` 或 `Alt+ArrowDown` 時，先 preventDefault，再算出新陣列交給 `store.reorder()`。

Vue 對有 key 的清單是搬移 DOM 節點，有些情況下 focus 會掉。所以排序後等下一個 tick，把 focus 設回同一個專案的按鈕。

提示文字目前是專案路徑，改成在路徑後面換行加一句按鍵說明，只加在可以排序的項目上。

### 6. 可以排序的範圍

組出一個 `canReorder` 狀態，拖曳和鍵盤都看它：

- `busy` 為 false。
- 清單沒有收合：專案數沒超過門檻，或已經按了 Show N more。

暫時項不能被拖，鍵盤也不能移動它。其他專案可移動範圍的上限是暫時項正下方。

## Risks / Trade-offs

- [拖曳時清單剛好因為徽章刷新而重新渲染] → 拖曳只用路徑辨識項目，位置在開始拖時量好。徽章刷新不改順序和高度，所以不影響落點。
- [拖曳中某個專案被外部移除（只會發生在另一個視窗）] → 後端比對會發現不是同一組路徑而回失敗，畫面彈回並跳 toast。這是可以接受的結果。
- [排隊中的存檔失敗時，畫面會一次跳回好幾步之前的順序] → 這是「回到最後一次存成功的順序」的必然結果。toast 會說明原因。
