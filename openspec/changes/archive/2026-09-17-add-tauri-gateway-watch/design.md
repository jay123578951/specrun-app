## Context

動機見 proposal.md 的 Why。這裡只記影響做法的現況與限制。

web 形態的監看住在 `server/utils/change-watcher.ts`：整個 server 共用一個監看、事件經 400 毫秒的尾端合併後廣播給所有訂閱者、切換目標專案時先停再重接。`server/api/watch.get.ts` 把它推播給瀏覽器，前端以瀏覽器內建的事件來源接收（自帶重連）。

桌面形態這側的既有零件：`src/api/desktop/projects.ts` 持有「目前是哪個專案」的執行期狀態，並提供 `resolveTarget()`（解開 symlink、取得檔案存取授權、確認是既存資料夾）；`src/api/desktop/paths.ts` 是 T3 為 park 快照做的純字串路徑計算，含 `isInside`；`src/api/desktop/shell.ts` 是外殼通道的薄層。

三個影響做法的限制：

- 外殼的監看通道把底層錯誤整個吞掉。監看建立之後失效（目錄被刪、監看本身出錯）沒有任何訊號送上來。
- 該通道的延遲合併只合併「多久收一批」，一批之內仍是逐則往上送。
- 監看的路徑必須落在檔案存取的授權範圍內，而授權是 `resolveTarget()` 的一部分。

## Goals / Non-Goals

**Goals:**

- `subscribeToChanges` 在桌面形態由這個形態自己服務，介面與語意對呼叫端完全不變。
- 切換、加入、移除專案後，監看跟著換目標，且這件事不外洩到畫面層。
- 環境診斷的即時刷新一項在桌面形態答得出明確的是或否。
- 刪掉桌面形態回頭呼叫本地 API server 的那段過渡程式。

**Non-Goals:**

- 不動 `server/` 底下任何檔案（web 形態還要用，T4b 才整批下線）。
- 不動 `src/App.vue` 與任何 store。
- 不擴監看範圍（Specs、Archived、parked 皆不在內）。
- 不改「連環變動合併為一則」的觀感——尾端合併的毫秒數沿用 400。

## Decisions

### 1. 合併收在 gateway 實作端，介面一個字不改

`subscribeToChanges` 對外仍是「給一個 callback、回傳取消訂閱」，且契約仍是「一批變動＝一則通知」。底層通道逐則送上來的事完全不外洩。

理由：契約明文寫「通知粗粒度，訂閱者收到就自行重取」。一趟重取實測要 1.2 秒以上（一次 CLI 呼叫加檔案讀取），把逐則交給呼叫端等於讓 App.vue 去承擔一個實作細節，而且一次 git 操作會變成數十趟。

替代方案：只倚賴底層通道的延遲合併。已否決——它每隔一個延遲週期就把累積的那一批送上來，連續寫入 30 秒的情境下會變成一路重取，比現在更糟。

### 2. 尾端合併 400 毫秒不變；底層的延遲合併只當作節流

畫面上「什麼時候真的重取」由這一層的 400 毫秒尾端合併決定，語意與 web 形態逐字相同：最後一則變動之後再過 400 毫秒才通知一次。底層通道的延遲只用來壓跨行程的訊息量，數值不寫進 spec。

理由：T2、T3 的先例都是「只換持有者與執行形態，不換語意」。而一趟重取本身就要 1.2 秒以上，底層延遲給 50 還是 200 毫秒在畫面上看不出來。

### 3. 切專案的重接由監看模組自己訂閱，不推給呼叫端

`src/api/desktop/projects.ts` 多一個「目前專案變了」的訂閱出口，監看模組訂閱它；加入、移除、切換三個動作改完狀態後各自送出一次。

理由：介面一動就波及 App.vue 與三個 store，而「切換之後監看要跟上」是實作細節不是畫面決策。web 形態的做法本質相同——那三支端點各自呼叫一次重接，只是重接的對象在 server 裡。

替代方案：把 `subscribeToChanges` 改成接受目標專案、由畫面端在切換後重新訂閱。已否決——契約裡「切換目標專案後通知來源跟隨」是 gateway 的責任，改成呼叫端負責等於把責任推出去。

### 4. 監看目標走 `resolveTarget()`，不走設定裡的原字串

理由有兩層，缺一不可：變動事件回報的是解開 symlink 後的實際位置，監看路徑不是同一個寫法時，`isInside` 會把每一則都判成範圍外；而且監看路徑必須先取得檔案存取授權，授權正是 `resolveTarget()` 做的事。

副作用要記著：App.vue 在掛載時就訂閱，早於專案清單載入。`resolveTarget()` 是非同步的，而 `subscribeToChanges` 同步回傳取消訂閱——接上的過程放著跑，取消訂閱時若還沒接上，要能取消掉那一輪。沿用 web 形態的做法：每次重接把一個計數加一，接上途中發現計數已變就把那一輪的結果丟掉。

### 5. `openspec/changes/` 監看不了就退一層看 `openspec/`，用絕對路徑判範圍

與 web 形態同一套降級：先試 `openspec/changes/`，該目錄還不存在時退一層監看 `openspec/`，等它被建出來。差別在過濾的依據——web 形態拿到的是相對檔名，這裡拿到的是絕對路徑陣列，改用 `paths.ts` 的 `isInside(路徑, changes 目錄)` 判斷，任一條路徑落在裡面就算一則。

不另造判斷工具：`isInside` 是逐片段比對、`..` 在比對前已收掉，正是這裡需要的語意。

### 6. 診斷的即時刷新一項語意改為「有沒有接上」

監看模組對外提供一個同步的「現在有沒有接上」，`diagnostics.ts` 直接讀它。無目標專案、或兩層目錄都監看不了時為否；接上之後恆為是。

理由：外殼的監看通道不回報中斷，桌面形態拿不到失效訊號。沿用 web 形態的「此刻是否仍有效」語意會在監看已死時仍宣稱它在運作，那是一句講不準的話。代價寫進 spec：專案資料夾被搬走之後那一行仍顯示已接上——但主區那時已經整片是「讀不到這個專案」，診斷區不必再說一次。

替代方案一：每次開 Settings 順便確認目標目錄還在。已否決——只驗得出「目錄不見了」這一種死法，別的死法照樣測不到，多一趟檔案查詢換來的仍是一句講不準的話。
替代方案二：桌面形態回未知。已否決——那一行從此永遠是佔位符，搬完之後畫面上看不出任何差別。

### 7. 訂閱建立本身不觸發一次通知

web 形態有「重連成功視同收到一次變動」的補償，因為斷線期間的變動不會重播。桌面形態的通知在同一個行程內直接傳遞，沒有可斷的傳輸通道，補償沒有觸發條件，整段拿掉。

切專案時的重接同樣不補發：切換動作本身已經重載了清單。

### 8. 過渡同步呼叫在本張刪除

`syncLocalServer`、三處呼叫與等待上限常數一併刪掉。那段程式自己的註解就寫著升級條件是「本地 API server 不再需要知道目前專案是哪個」——監看是它手上最後一項需要目標專案的東西，本張達成。

順帶解掉它那個表達不出來的情形：移除清單裡最後一個專案時，那個掛載點需要一個路徑、講不出「沒有目標專案」，server 會停在剛被移除的專案。刪掉之後這個情形不存在。

### 9. 多個訂閱者的集合保留

桌面形態只有一個視窗、一個訂閱點，理論上可以簡化成單一訂閱者。仍保留集合：成本是一個 Set，而契約寫的是「通知所有訂閱者」，為了省一個 Set 去改契約不划算。

## Risks / Trade-offs

- **監看已死但診斷說它活著** → 已接受並寫進 spec（見決策 6）。觸發情境只有「目標專案資料夾被搬走或刪除」，那時主區已明確呈現該專案讀不到。
- **兩層合併疊在一起，單次存檔的延遲比現在略長** → 底層延遲加上 400 毫秒的尾端合併。相對於一趟重取的 1.2 秒，這段差別在畫面上看不出來；底層延遲不寫進 spec，實作端可調。
- **App.vue 掛載時就訂閱，早於專案清單載入** → 接上的過程非同步進行，以計數丟棄過期的那一輪（見決策 4）。取消訂閱在接上之前發生時，接上後要立刻收掉。
- **`.git` 底下的變動不觸發通知** → 本來就不該觸發：監看範圍是 `openspec/changes/`，parked 目錄的外部變動不刷新是既有行為，不是本張帶進來的。
- **web 與桌面兩形態的診斷欄位語意在本張之後不完全一致** → web 形態答的是「此刻是否仍有效」，桌面形態答的是「有沒有接上」。這個不一致只活一張的時間，T4b 把 web 形態整批下線。

## Migration Plan

沒有資料遷移，也沒有持久化格式變動。切換是純程式碼層：`desktopGateway` 補上 `subscribeToChanges`，該方法不再落到 web 形態的實作。

回退：把 `desktopGateway` 的那一行拿掉即可退回目前狀態（桌面形態沿用 web 形態的推播實作）；過渡同步呼叫的刪除要一併還原，否則退回後切專案時 server 上的監看不會跟上。

`server/api/watch.get.ts` 與 `server/utils/change-watcher.ts` 在本張完全不動，web 形態的行為零變化。
